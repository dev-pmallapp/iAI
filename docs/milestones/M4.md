# Milestone 4 — Development pack

**Theme:** forge, ported onto the binding abstraction — the baseline that
validates M1.
**Estimate:** L · **Stories:** 5 · **Depends on:** M2, M3

Express `dev` as a `DomainBinding` and nothing more. This milestone ships before
the life domains on purpose: `dev` is the one domain where the loop is already
proven, so it is the honest test of whether the abstraction holds. If `dev`
cannot be expressed without a special case in core or in a Tier-1 skill, the
abstraction is wrong, and M5 through M7 do not start.

## Stories

### S4.1 — Dev binding and build-target detection

**Unit:** one build system or binding sub-spec · **Size:** M · **Labels:** `type:story`, `domain:dev`, `iai`

Write `skills/dev/domain.md` and the detection layer that identifies build
targets from build definition files. The build definition file — not the
directory and not the language — is the target's identity.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: `devBinding` loads through the M1 registry with no edit to any file
      under `packages/core/src`.
- [ ] ISC-2: Detection identifies the expected target names from a fixture for
      each of `CMakeLists.txt`, `Makefile`, `go.mod`, `pyproject.toml`,
      `setup.py`, `Cargo.toml`, `package.json` and `BUILD.bazel`.
- [ ] ISC-3: The build-target-to-task mapping is 1:1 in both directions on every
      fixture; a decomposition splitting one target's sources across two tasks is
      refused by `size`.
- [ ] ISC-4: Two build definition files of the same kind in one directory yield
      an ambiguous verdict from `size` rather than an arbitrary pick.
- [ ] ISC-5: The rungs `compile`, `unit`, `integration` and `review` are ordered
      and unskippable — a target with no declared test command stays at
      `rung:compile` and does not pass `rung:unit` by having nothing to run.
- [ ] ISC-6: `gate.autoDeny` blocks `gh pr merge` for every actor at every rung,
      and blocks a review whose reviewing agent is the authoring agent.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| `devBinding` with UnitSpec, VerifySpec, GateSpec and EvidenceSpec | iai-domain-dev | `skills/dev/domain.md`; registered from outside core |
| Build definition file detection across the eight ecosystems | iai-domain-dev | Target identity within the file, per ecosystem |
| Granularity and rung-promotion rules wired to `size` | iai-domain-dev | Ambiguity is a verdict, not a guess |

**Verification:** One fixture repository per ecosystem yields the expected target
inventory; the registry loads the binding with core untouched; the negative
fixtures for split targets, duplicate build files and skipped rungs each produce
the documented refusal.

### S4.2 — Config-free project context discovery

**Unit:** one context source · **Size:** M · **Labels:** `type:story`, `domain:dev`, `iai`

Derive every piece of project context from git and the root documents. There is
no config file, because a config file drifts from the documents humans actually
read within a month.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: Owner, repo and default branch are derived from
      `git remote get-url origin` plus `gh repo view --json defaultBranchRef`;
      with no remote configured, Phase 0 hard-fails rather than assuming.
- [ ] ISC-2: The `## Build Targets` table is parsed by header name — reordering
      columns and adding extra columns changes nothing, and renaming a required
      header produces a named parse failure.
- [ ] ISC-3: The `## Commands` block yields build, test, lint and integration
      commands with `{target}`, `{target_dir}`, `{repo_root}` and `{issue}`
      substituted; a missing `Passes when:` line defaults to exit-code-0 and
      records that assumption in the evidence artifact.
- [ ] ISC-4: No file outside git, `README.md`, `ARCHITECTURE.md`,
      `CONTRIBUTING.md`, `CLAUDE.md`/`AGENTS.md` and `docs/milestones/M*.md` is
      read for context, and no `iai-config.*` is consulted — asserted by a test
      that fails on any other read.
- [ ] ISC-5: In a multi-repo fixture, targets resolve to their owning repo via
      `README.md`'s `## Repositories` while every issue is created in the primary
      repo.
- [ ] ISC-6: Every absent source degrades loudly: the missing input is named in
      the ISA or the evidence artifact, and where it changes a verdict, on the
      issue.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| Git-derived identity and the seven-step Phase 0 sequence | iai-domain-dev | No remote is a hard failure; there is no offline mode |
| Header-name parsers for Build Targets and Commands | iai-domain-dev | Placeholder substitution plus the `Passes when:` predicate |
| Multi-repo resolution and loud degradation for absent sources | iai-domain-dev | Issues stay in the primary repo regardless of target repo |

**Verification:** A fixture repo with columns reordered, extra columns added and
a header renamed produces the three documented outcomes; the read-tracing test
proves no other file is consulted; a fixture with `CONTRIBUTING.md` removed keeps
tasks at `rung:compile` and stamps the reason into the artifact.

### S4.3 — Branch, PR and integration model

**Unit:** one branch or PR operation · **Size:** M · **Labels:** `type:story`, `domain:dev`, `iai`

Bind the branch and PR model to `dev`. The closing-keyword hazard is the single
most common way a naive implementation silently corrupts state, so it gets an
explicit closure step rather than a comment warning about it.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: Slug generation follows the four-step rule and reproduces the three
      documented examples exactly, including the 40-character truncation with the
      trailing `-` stripped afterwards.
- [ ] ISC-2: Story branches are cut from the default branch and task branches
      from the story branch; a task branch cut from the default branch is
      refused.
- [ ] ISC-3: Task PRs open as drafts targeting the story branch, and a task PR
      targeting the default branch is refused before creation.
- [ ] ISC-4: The integration PR body carries one `Closes #N` per line for the
      Story and each of its tasks; a comma-separated list fails the linter.
- [ ] ISC-5: After a task PR merges into the story branch — where no closing
      keyword fires — the task issues are nonetheless closed, by the explicit
      `gh issue close` step.
- [ ] ISC-6: `iai dev abort --story {n}` returns every open PR under the Story to
      draft, removes `gate:approved`, applies `status:blocked`, and posts the
      reason under `## iai-gate`.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| Slug rule and branch creation with base-branch enforcement | iai-domain-dev | Task branches cut from the story branch only |
| Draft task PR and integration PR construction | iai-domain-dev | One `Closes #N` per line; never merged by iAI |
| Explicit task closure and the story kill switch | iai-domain-dev | Works around the default-branch-only closing keyword |

**Verification:** The slug suite reproduces every documented example; a fixture
Story is driven to a ready integration PR with an unmerged head and a correct
`Closes` block; the abort command is run mid-flight and every open PR returns to
draft with the Story blocked.

### S4.4 — Dev leaf skills

**Unit:** one leaf skill · **Size:** L · **Labels:** `type:story`, `domain:dev`, `iai`

Write `code-review`, `debug`, `refactor`, `test-gen`, `arch-audit`, `dep-audit`
and `release`. Leaves are dispatched by a Tier-1 verb through the binding; the
lifecycle never calls them directly.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: All seven skills exist under `skills/dev/` with frontmatter carrying
      `tier: "2"`, `domain: "dev"`, a routing `category` rather than a model ID,
      and an `invoked-by` verb.
- [ ] ISC-2: Every leaf is reached through a Tier-1 verb and the resolved
      binding; a direct router invocation without a resolved `domain:dev` label
      is refused.
- [ ] ISC-3: `code-review` refuses when the reviewing agent is the authoring
      agent, and every finding cites a `file:line` or an `ISC-N` rather than a
      style preference alone.
- [ ] ISC-4: `debug` refuses a fix that has no reproduction, and emits a
      regression test alongside the minimal diff.
- [ ] ISC-5: `test-gen` produces cases from the ISA's `ISC-N` claims and the Test
      Strategy `anchors_to` column with zero implementation-file reads during
      generation, asserted by read tracing.
- [ ] ISC-6: `refactor` discharges its proof obligation — the same test set green
      before and after, with the test files unchanged in the same commit — or it
      fails.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| `code-review` and `debug` | iai-skills | Self-review refused; reproduction precedes fix |
| `refactor` and `test-gen` | iai-skills | Proof obligation; claims-not-code test generation |
| `arch-audit` and `dep-audit` | iai-skills | Table-versus-tree drift; findings carry severity, not auto-bumps |
| `release` | iai-skills | Changelog from `#{issue}:` prefixes; tag and merge are human |
| Leaf dispatch through the binding, plus frontmatter lint | iai-domain-dev | `binding.unitOfWork.leafSkill` is the only entry point |

**Verification:** Each leaf runs against the fixture repository through its
dispatching Tier-1 verb; the direct-invocation refusal, the self-review refusal
and the no-reproduction refusal each produce the documented block; read tracing
proves `test-gen` never opened the implementation.

### S4.5 — forge parity validation

**Unit:** one parity scenario · **Size:** M · **Labels:** `type:story`, `domain:dev`, `iai`

Prove on a fixture repository that iAI reproduces forge's end-to-end pipeline,
including on instances lacking the sub-issue GraphQL API, and document every
intentional behavioural difference rather than discovering it in production.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: The conformance suite drives the fixture repository from milestone
      to merged integration PR, stopping at exactly the three gates and at no
      other point.
- [ ] ISC-2: With the sub-issue GraphQL API disabled, the same run completes
      using `Parent: #N` body links plus a `## Tasks` checklist, and the
      resulting issue graph is equivalent to the GraphQL run.
- [ ] ISC-3: Every forge pipeline step has an iAI step with the same observable
      outputs, or a row in the documented diff explaining the intentional change.
- [ ] ISC-4: `docs/parity/forge-diff.md` enumerates each behavioural change with
      a rationale, and the suite fails when an output difference appears that is
      not listed there.
- [ ] ISC-5: A search of `packages/core` and the Tier-1 skills for dev-specific
      branching — a `domain === "dev"` comparison, a build definition filename,
      or a compiler noun — returns zero matches outside test fixtures.
- [ ] ISC-6: The suite runs in CI on every PR and commits its evidence artifact
      with an SHA-pinned permalink.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| Fixture repository and the end-to-end conformance harness | iai-domain-dev | Milestone through merged integration PR, three gates |
| Sub-issue fallback scenario and issue-graph equivalence check | iai-domain-dev | GraphQL disabled; `Parent: #N` links plus checklist |
| `docs/parity/forge-diff.md` and the no-dev-branch assertion | iai-domain-dev | The abstraction-leak risk row closes here |

**Verification:** Both conformance runs — with and without the sub-issue API —
complete on the fixture repository with only the three gate pauses; the issue
graphs are compared structurally; an unlisted output difference is injected and
the suite fails as designed.

## Exit criteria

- [ ] The fixture repository runs from milestone to merged integration PR with no
      manual intervention other than the three gates.
- [ ] No dev-specific branch exists anywhere in `packages/core` or in the Tier-1
      skills.
- [ ] `devBinding` is registered from outside core and resolves via the
      `domain:dev` label.
- [ ] Build-target detection passes for all eight build definition file kinds.
- [ ] Task issues close explicitly, and the integration PR carries one `Closes
      #N` per line.
- [ ] `docs/parity/forge-diff.md` is committed and the conformance suite is a
      required CI check.
- [ ] The abstraction-leak risk row is closed: `dev` needed no special case, or
      the milestone halts and the design is revised.

## Dependencies and sequencing

**Strictly ordered.** S4.1 lands first — the binding is what every other story in
this milestone resolves through, and without it the Tier-1 verbs have no `dev`
unit of work to decompose against.

**Parallel.** S4.2, S4.3 and S4.4 are independent after S4.1. Context discovery
reads root documents, the branch model writes git and GitHub, and the leaf skills
are docs targets; they share only the binding. Three engineers can take them
concurrently.

**Ordered last.** S4.5 is by construction the final story: it exercises
everything the other four produce. Starting it early yields a suite that tests
stubs. Its `forge-diff.md` task can begin earlier, since documenting an intended
difference does not require the difference to be implemented yet.

**Gate on the milestone, not the story.** M5, M6 and M7 are blocked on this
milestone's exit criteria rather than on any single story. If S4.5 shows `dev`
required a special case in core, treat that as a halt condition for the whole
plan and reopen the M1 binding design before any life domain starts.
