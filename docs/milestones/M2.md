# Milestone 2 — Universal lifecycle

**Theme:** The fourteen Tier-1 verbs, none of which may name a domain.
**Estimate:** XL · **Stories:** 5 · **Depends on:** M1

Write the universal loop once. Every skill here is a docs target — markdown with
frontmatter, not compiled code — so verification is the frontmatter linter, an
idempotency re-run test, and the domain-agnosticism lint that fails any skill
body naming a domain outside a reference citation. If a verb needs to know it is
running against software, the abstraction from M1 is wrong and you stop here.

## Stories

### S2.1 — Kernel reference documents

**Unit:** one reference document · **Size:** L · **Labels:** `type:story`, `domain:dev`, `rung:compile`, `iai`

Write the twelve contract documents that skills read by explicit path. References
are deliberately not skills: the host never enumerates them, so they cost zero
skill-tool budget and a contract exists in exactly one place.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: All twelve files exist at `references/<name>.md` under the exact
      names `context-discovery`, `gh-operations`, `gh-error-handling`,
      `verification`, `data-classification`, `model-routing`, `domain-binding`,
      `evidence-artifacts`, `branch-and-pr-model`, `workflow-states`,
      `isa-format` and `sizing-criteria`.
- [ ] ISC-2: A duplicate-contract lint fails when a skill body restates the
      sentinel rules, the at-most-one-`status:` invariant or the commit-prefix
      regex instead of citing the owning reference.
- [ ] ISC-3: `references/model-routing.md` is the only file outside
      `packages/core/src/routing` containing a literal model ID, asserted by
      lint.
- [ ] ISC-4: The installed skill roster contains zero `references/` entries, so
      no reference description enters a session's working set.
- [ ] ISC-5: No skill authored in this milestone cites more than three
      references, counted by lint over the skill bodies.
- [ ] ISC-6: Each reference's normative statements are reconciled against
      `docs/design/` and against the M1 implementation, with the reconciliation
      table committed to the evidence artifact and zero unresolved conflicts.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| context-discovery, gh-operations, gh-error-handling | iai-references | Documents M1 S1.3 behaviour, including the closing-keyword hazard |
| verification, workflow-states, branch-and-pr-model | iai-references | The three doctrines plus the single-command transition shape |
| data-classification, model-routing | iai-references | The only document permitted to name model IDs |
| domain-binding, evidence-artifacts | iai-references | Mirrors the M1 interface and the 60,000-char budget |
| isa-format, sizing-criteria | iai-references | ISA v2.21.0 keys, 17 sections, `ISC-N` claim grammar |

**Verification:** The frontmatter linter and the duplicate-contract lint both
pass; a roster dump proves no reference is registered as a skill; the
reconciliation table shows every reference claim matched to design or code.

### S2.2 — Planning skills

**Unit:** one Tier-1 skill · **Size:** L · **Labels:** `type:story`, `domain:dev`, `rung:compile`, `iai`

Write `goal-create`, `story-create`, `story-design` and `story-test-plan`. These
four turn intent into pre-registered, machine-checkable claims — the ISA is the
contract everything downstream verifies against.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: `goal-create` creates one milestone whose description carries a
      `| Feature | Description |` table and posts a back-link comment on the
      goal's `G0` line; a second run creates no second milestone.
- [ ] ISC-2: `story-create` creates exactly one Story per feature-table row, each
      labelled `type:story`, exactly one `domain:*` and `iai`, and assigned to
      the milestone; run against a milestone missing one Story it creates that
      one and nothing else.
- [ ] ISC-3: `story-design` writes `docs/design/stories/{n}.md` with the ISA
      frontmatter keys, all seventeen body sections, at least one
      `- [ ] ISC-N:` claim, and posts a `## iai-design` sentinel carrying an
      SHA-pinned permalink.
- [ ] ISC-4: `story-test-plan` writes `docs/test-plans/{n}-plan.md` in which
      every `ISC-N` in the ISA appears in the `anchors_to` column of at least one
      case, and no case anchors to a claim that does not exist.
- [ ] ISC-5: Each of the four skills resolves the binding from the Story's
      `domain:` label; run against a Story with no `domain:*` label, each emits
      the hard-failure block rather than assuming a domain.
- [ ] ISC-6: All four pass the domain-agnosticism lint — no body contains `dev`,
      `trade`, `health`, `wealth` or `know` outside a `references/` citation
      path.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| `goal-create` | iai-skills | TELOS `G0` to milestone; back-link comment is part of the contract |
| `story-create` | iai-skills | Feature-row to Story; idempotent by row identity |
| `story-design` | iai-skills | ISA v2.21.0; claims are pre-registered before any work |
| `story-test-plan` | iai-skills | Claims to P0/P1/P2 cases via `anchors_to` |
| Idempotency re-run and domain-agnosticism lint harness | iai-skills | Shared by S2.2 through S2.5 |

**Verification:** Each skill runs twice against the same fixture repository and
the second run makes zero mutations; the ISA and plan produced are parsed
mechanically and every claim maps to at least one case; both lints pass.

### S2.3 — Execution skills

**Unit:** one Tier-1 skill · **Size:** L · **Labels:** `type:story`, `domain:dev`, `rung:compile`, `iai`

Write `task-create`, `task-do` and `task-verify`. These are the highest-traffic
verbs in the system and the ones most likely to corrupt state, so idempotency and
explicit task closure are load-bearing, not polish.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: `task-create` opens one sub-issue per `binding.unitOfWork` item,
      each anchored to at least one `ISC-N`, labelled `type:task` and the
      parent's `domain:*`, and adds a `## Tasks` checklist to the Story.
- [ ] ISC-2: Dependencies appear as `Blocked by: #N` lines matching the parent
      checklist order; a cyclic dependency is refused with the hard-failure
      block rather than partially created.
- [ ] ISC-3: `task-do` creates `task/{n}-{slug}` cut from the story branch,
      commits with `#{issue}: ` prefixes, and opens a draft PR targeting the
      story branch; a PR targeting the default branch is refused before creation.
- [ ] ISC-4: Re-running `task-do` on a task that already has a branch, commits
      and a draft PR creates zero new branches, zero new PRs and zero duplicate
      commits.
- [ ] ISC-5: `task-verify` writes `docs/evidence/{n}-{ts}.md`, posts
      `## iai-evidence`, marks the PR ready, applies `status:resolved` in one
      `gh issue edit` paired with `--remove-label`, and closes the issue
      explicitly.
- [ ] ISC-6: `task-verify` refuses to resolve a task whose anchored `ISC-N` has
      no evidence on disk, emitting the hard-failure block.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| `task-create` | iai-skills | Sub-issue parenting with the `Parent: #N` fallback |
| `task-do` | iai-skills | Branch, commit prefix, draft PR against the story branch |
| `task-verify` | iai-skills | Evidence before label; explicit `gh issue close` |
| Story roll-up on last-task-resolved | iai-skills | Step 8 of the pipeline; derived, not commanded |

**Verification:** A fixture Story is driven from `task-create` through
`task-verify` twice; the second pass mutates nothing; the task issues are closed
even though no closing keyword fired, and each carries evidence on disk.

### S2.4 — Closure skills

**Unit:** one Tier-1 skill · **Size:** M · **Labels:** `type:story`, `domain:dev`, `rung:compile`, `iai`

Write `story-verify` and `learn`. `story-verify` re-grounds the plan against what
actually shipped and stops at the merge; `learn` extracts what the milestone
taught and closes it.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: `story-verify` reconciles the planned cases against the units
      actually present on the story branch and records every drift row before
      executing anything.
- [ ] ISC-2: It executes the verification itself rather than reading a prior
      result, and its `## iai-verdict` first line matches
      `#{n}: (PASS|FAIL|TESTS_SKIPPED|PARTIAL)`.
- [ ] ISC-3: The integration PR body carries one `Closes #N` per line for the
      Story and every task; a comma-separated list fails the linter.
- [ ] ISC-4: No path in `story-verify` invokes `gh pr merge` — asserted by a lint
      over the skill body and by a runtime guard that blocks the call.
- [ ] ISC-5: `learn` opens knowledge-base PRs, writes `MEMORY/` entries tiered
      A/B/C, posts `## iai-learnings`, and closes the milestone only once every
      Story under it is closed.
- [ ] ISC-6: Re-running either skill on an already-closed Story or milestone
      produces no duplicate PR, comment or `MEMORY/` entry.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| `story-verify` | iai-skills | Re-grounding, verdict, integration PR marked ready |
| `learn` | iai-skills | KB PRs plus Cortex-lite `MEMORY/` entries |
| Never-merge guard and integration-PR body linter | iai-skills | One `Closes #N` per line; `gh pr merge` blocked |

**Verification:** A fixture Story reaching `PASS` yields an integration PR that
is ready and unmerged, with one `Closes` line per issue; a forced `gh pr merge`
attempt is blocked; the milestone closes only after the last Story closes.

### S2.5 — Continuity skills

**Unit:** one Tier-1 skill · **Size:** L · **Labels:** `type:story`, `domain:dev`, `rung:compile`, `iai`

Write `checkpoint`, `resume`, `status`, `size` and `replan`. Agents die; sessions
compact; engineers hand off. These five make that recoverable by re-reading the
record rather than trusting a transcript.

**Acceptance criteria** (these seed the ISA claims):
- [ ] ISC-1: `checkpoint` writes a `## iai-checkpoint` comment plus a `MEMORY/`
      entry naming the active issue, open branches, uncommitted paths and the
      next action — enough to cold-start with no prior context.
- [ ] ISC-2: `resume` rebuilds context from disk and GitHub only; given a
      checkpoint that disagrees with the labels it emits a reconciliation note
      and proceeds on the record.
- [ ] ISC-3: `status` renders six view modes, and with `gh` unavailable falls
      back to a local-only report that names each unavailable field rather than
      omitting it.
- [ ] ISC-4: `size` posts `## iai-effort` with an S/M/L/XL verdict derived from
      `references/sizing-criteria.md` and the binding's thresholds, and applies
      `status:blocked` when the unit exceeds `maxSize`.
- [ ] ISC-5: `replan` closes superseded task issues with a stated reason, re-cuts
      the affected tasks and updates the ISA claims, leaving no orphan issue and
      no claim without a task.
- [ ] ISC-6: All five pass the idempotency re-run test and the
      domain-agnosticism lint.

**Indicative tasks:**
| Task | Build target | Notes |
|------|--------------|-------|
| `checkpoint` | iai-skills | Also triggered by `session.idle`; cold-start sufficiency is the bar |
| `resume` | iai-skills | Re-read, never remember; reconciliation note on disagreement |
| `status` | iai-skills | Six view modes; local-only fallback names its gaps |
| `size` | iai-skills | Binding supplies thresholds; the reference supplies the method |
| `replan` | iai-skills | Requirement-change detection and incremental re-cut |

**Verification:** A checkpoint is taken, the session is discarded, and `resume`
in a fresh session reconstructs the working set from the record alone; `status`
is run with `gh` removed from `PATH` and degrades loudly; `replan` on a mutated
fixture leaves a consistent issue graph.

## Exit criteria

- [ ] Every Tier-1 skill passes the domain-agnosticism lint: no skill body
      contains the literal strings `dev`, `trade`, `health`, `wealth` or `know`
      outside a reference citation.
- [ ] Every Tier-1 skill passes the idempotency re-run test: a second identical
      invocation produces zero mutations.
- [ ] All fourteen verbs exist under `skills/` and pass the frontmatter linter on
      the host-intersection field set.
- [ ] All twelve references exist, are cited by path, and are absent from the
      installed skill roster.
- [ ] No skill cites more than three references.
- [ ] Measured token cost of Tier 0 plus one Tier-1 verb is recorded in the
      evidence artifact, closing the context-budget risk row.

## Dependencies and sequencing

**Strictly ordered.** S2.1 lands first. Every other story in this milestone cites
references by path, and a skill written before its contract exists will restate
the contract — exactly the drift the reference layer exists to prevent.

**Parallel.** After S2.1, the four skill stories are independent by pipeline
stage and can run concurrently. S2.2 and S2.3 share the lint harness introduced
in S2.2's last task, so land that task early and let S2.3 through S2.5 consume
it.

**Ordered within the loop.** S2.4 depends on S2.3 for evidence artifacts to roll
up, and on S2.2 for a test plan to re-ground against; take it after both are
merged. S2.5 is the least coupled and can start any time after S2.1, but its
`replan` task needs `task-create` from S2.3 to have something to re-cut.

**Downstream.** M3 needs the Tier-1 verbs to exist before agents can be given
phase assignments, and M4 needs all fourteen before the dev binding can be
proven not to require a special case.
