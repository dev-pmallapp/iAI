## The finding that outranks the table

**No `gh` exit code distinguishes transient from permanent.** Exit 1 is returned
for an unknown subcommand, an unknown flag, a missing argument, a GraphQL
not-found and a rejected credential alike — a 404 and a rate limit produce the
same code.

Every row therefore classifies `fatal`. Retry decisions cannot come from exit
status at all; they come from response headers and text, which is precisely why
Decision 1's response envelope exists. **A future reader who "fixes" this by
marking exit 1 retryable would make every permanently broken invocation retry
forever.**

`0` is classified `fatal` deliberately, so a caller who consults
`classifyExitCode` without first checking `exitCode === 0` fails safe rather
than re-running a side-effecting command because "retryable" looked true.

Unmapped codes default `fatal` (`docs/milestones/M1.md:140-141`), so an
incomplete table halts a batch rather than retrying forever. That default is
what makes authoring the table safe at all.

## Decision 1 — absence of a header is not evidence of absence of a limit

`gh api --include` appears nowhere in this repository, so the common case is
that the adapter captured no headers. A `403` with no `x-ratelimit-remaining`
must therefore still classify as possibly rate-limited and still yield a resume
plan: treating a real rate limit as fatal abandons a batch that would have
succeeded on retry.

Header lookup is case-insensitive per RFC 7230 §3.2. A literal
`headers["x-ratelimit-remaining"]` would silently miss `X-RateLimit-Remaining`,
which is the casing many HTTP clients emit — and that miss would look exactly
like "not rate limited".

## Case 11 is the resume test that matters

Per Note 3 of `docs/test-plans/21-plan.md`. Case 10 checks the plan names the
right remainder; that is half the property. Case 11 simulates two invocations,
unions the emitted sets and asserts **zero duplicates and a set size of 10**.

A plan that re-emits a processed item duplicates issues, which is the failure
`docs/design/04-domain-dev.md:505` describes as "a re-run duplicates".

Items carry a stable `id` rather than an array index, so exactly-once is
provable even if a caller reconstructs the batch differently. A second test
covers a nested failure inside the resumed remainder and derives the second plan
from the **original** batch — deriving it from the first plan's remainder would
shift indices and corrupt the resume position.

## Invented constants, labelled as such

`BACKOFF_BASE_MS = 1000`, multiplier 2, cap 30 s, 5 attempts. No base delay,
cap, jitter or attempt limit is stated anywhere in the tree —
`docs/design/04-domain-dev.md:505` and `ARCHITECTURE.md:194` say only "backs off
exponentially".

Chosen independently of `docs/design/02-roles.md:186`'s "retry up to 3 times on
transient failure", which governs **test-run** retries rather than `gh` calls.
That distinction is noted in the module rather than the number silently
borrowed, because borrowing it would imply an authority that does not exist.

The delay is returned as a value; the adapter sleeps. Sleeping, counting
attempts and re-invoking are all effects and none of them happens here
(Decision 4).

## Decision 7 — the one sanctioned scraping exception, contained

`gh issue create` has no `--json` flag, so the new issue number exists only in
the URL printed to stdout, which `docs/design/09-security.md:192` forbids
reading. Exactly one parser may read unstructured stdout; it does nothing but
extract a trailing issue number from a GitHub issue URL, and a line that is not
such a URL is a **typed failure, not a guessed integer**. A length guard was
added after a hostile-input test caught an unbounded accept.
