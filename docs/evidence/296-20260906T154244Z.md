## Adding the directory was not enough, and that is the finding

Before this task `claim-lint` printed **one conflated total**. Adding `skills/`
moved it by exactly **1** — the `.gitkeep` — inside a total dominated by
`docs/`. So **"`skills/` is in scope and empty" was indistinguishable from
"`skills/` is not in scope"** from the tool's own output.

The only assertion available without a denominator is
`SCOPE_DIRS.includes("skills")`, which proves *the constant changed*, not that
the walk reaches the tree. **That is a restated-config test, not a behavioural
one** — precisely the shape that ships green and wrong.

The denominator is the same medicine two sibling rules already take, for the
same disease: `testplan-corpus` (#289) and `design-spine` (#294) both print
counts because, as `scripts/claim-lint.ts` says of the first, it *"is this
repository's standing example of a check that passes while checking nothing"*.

`discoverScopeFiles` returns the groups and the flat scan list is **derived**
from them, so the printed breakdown and the actual scan cannot disagree, and the
per-scope counts are asserted to **sum to the total**.

### N2 is the whole task in one mutation

`skills` present in the constant, absent from the traversal. **Every assertion
passed except one**: the run-time equality between the printed `skills` count
and the files actually on disk under `skills/`.

`SCOPE_DIRS.includes("skills")` passed. The CONTRIBUTING agreement passed. The
"every scope prints a line" test passed. The sum-to-total passed, because the
group was present and simply held zero files.

**Without the disk-equality assertion, #296 ships green with `skills/`
unscanned** — the directory in the config, the rule never running, and the
document truthfully describing a scope the linter does not honour. That is the
failure mode this task exists to prevent, reproduced exactly.

### N5 — the flip behaves as designed

A real `SKILL.md` was written into `skills/story-design/`. Exactly **one** test
went red: *"skills/ contains zero SKILL.md files today — #296 is not yet

the change automatically** (`scope skills 2 files`, total 102), which is the
point of writing them as run-time equalities: the four flips at #42-#45 cannot
be fudged, because the equality is read from disk on both sides and never needs

## Case 24 was mis-pointed — amendment 5, and a third occurrence

The case named `bun run claim-lint` for a property that tool cannot compute:
whether a **constant** holds a value, or whether a **comment** exists.
`claim-lint` has no rule that reads its own `SCOPE_DIRS`.

**Third occurrence of the category error recorded as amendments 1 and 3, in
three consecutive tasks** — and the sharpest, because unlike the first two it
*looks* correctly pointed. `scripts/claim-lint.ts` genuinely **is** inside
claim-lint's scanned population; it lives under `scripts/`. **Being scanned is
not being the subject of an assertion.** That distinction is the one the
previous two amendments did not have to make, and it is the one to carry
forward.

## The defect this task would have manufactured

`CONTRIBUTING.md`'s claim-lint section said the scope was *"`docs/`, `scripts/`,
`.github/` and the root markdown set"*. **Adding `skills/` makes that sentence
false** — #296 would have created the exact defect #295 had just fixed, in the
adjacent paragraph of the same file, and #295's case 23 would not have caught it
because it covers only the skill-lint section.

It now carries a scope table asserted against the exported `SCOPE_DIRS` in both
directions, reusing #295's mechanism. The **root-markdown pseudo-scope** is not
a member of `SCOPE_DIRS`, so it is checked explicitly and excluded from the set
comparison deliberately rather than passing or failing it by accident.

## A mutation whose diagnosis pointed away from the culprit

N3 was first run by replacing the `skills` row with an empty string. The failure
reported was *"CONTRIBUTING.md's scope table must document the root
pseudo-scope"* — **naming the wrong row**.

The cause was the mutation, not the test: a **blank line terminates a markdown
table**, so the row scanner stopped before reaching the `<root>` row. Re-run as
a clean deletion, it failed with the correct diagnostic, *"SCOPE_DIRS contains
`skills`, which CONTRIBUTING.md's scope table does not document"*.

Recorded because the misleading first result cost real time and matches the
`gh pr list` lesson of #46's artifact: **the first diagnosis points away from
the culprit**, and both tables in this repo are now parsed by a scanner with
this property. Both are protected — a truncation always changes the row count or
drops a member, and both tables assert row count *and* set equality — but the
**message** can still name the wrong row.
