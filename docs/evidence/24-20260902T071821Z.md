## The argv, decided here because none existed

iAI has no first-party `gh pr create` anywhere in the tree. The only one that
exists is quoted as **forge's** at `docs/design/verification-pass.md:281` and
covers only `--draft --base`. Flags for title, body, head, repo and reviewers
were all unstated, so this task decided them and the golden test is now the
record:

```
gh pr create --repo <owner>/<name> --draft --base <base> --head <head> --title <t> --body <b>
```

`--draft` is unconditional: `PrCreateInput` has no field that can disable it, so
a non-draft PR is not constructible. `CONTRIBUTING.md:335` and
`docs/design/02-roles.md:183` both require draft-by-default, and making it a
parameter would make the requirement a convention.

## Three judgement calls

**`renderPrBody` takes an explicit `kind` discriminator.** Refusing `Closes` on
a task PR requires knowing which kind of PR is being built, and inferring it
from which fields happen to be present would make a security-relevant rule a
guess about caller intent. `Closes` on a task PR is refused because it targets
the story branch and would never fire (`03-workflow.md:341`) — silently emitting
a directive that does nothing is worse than refusing it.

**`defaultBranch` is an explicit input.** Detecting a task PR aimed at the
default branch needs its name, and this layer cannot discover it — that is
Phase 0 context discovery, owned by M4 (`docs/milestones/M4.md:74-76`). Same
shape as Decisions 1 and 6.

**Case 21 matches argv elements exactly, not by substring.** `prView`'s refusal
message legitimately names `mergeCommit`, which contains the substring "merge".
A substring check would false-flag it. See below.

## The naive-substring trap, now three instances in one Story

| Where | The token | Why a substring check is wrong |
|---|---|---|
| `types.ts` comment | "fetched" | prose, not a `fetch(` call |
| `errors.ts` comment (#25) | a verbatim quote of `09-security.md` | prose again |
| `pr.ts` | `mergeCommit` | a legitimate `--json` field name |

The lint rule is correct in all three cases: `FETCH_CALL_RE` is
`/\bfetch\s*\(/` and case 21 compares argv elements with `===`. It is the
**grep-based verifier** that produces the false positives.

`docs/test-plans/21-plan.md` case 2 specifies "`grep` over the directory ... 0
occurrences of all three tokens". **That case belongs to #253 and should be
written against call and element forms, not substrings**, or it will fail on
correct code. Recorded here rather than silently working around it.
