## Six coordinated edits, not five

The issue body and the handoff both enumerate five. There is a sixth, and it was
found by measurement rather than by reading.

Bun resolves a workspace package by name **only from a package that declares it
as a dependency**. It writes scoped symlinks — `packages/adapter-claude/node_modules/iai-core`
— and no root-level ones; the repo root has no `iai-*` link at all, and
`packages/core` had no `node_modules` before this task. Case 6 requires an
import **by package name**, so `packages/core/package.json` now carries
`"devDependencies": { "iai-domain-null": "workspace:*" }`.

1. `packages/domain-null/package.json`, with `"dependencies": { "iai-core": "workspace:*" }`
   **and** the `"bun": "./src/index.ts"` export condition. The condition is
   what makes a name-import work with no prior build; deleting it (control run)
   yields `Cannot find package 'iai-core'`. Key order `types` → `bun` →
   `default` is load-bearing, since conditions match top-to-bottom.
2. `packages/domain-null/tsconfig.json` in the adapter shape, with
   `"references": [{ "path": "../core" }]`.
3. Root `tsconfig.json` `references` — hand-maintained, not globbed. `build`
   and `lint` auto-discover via `readdirSync`, but **`typecheck` silently skips
   a package with no reference**.
4. `ARCHITECTURE.md` Build Targets row.
5. `bun install` — 12 added lines in `bun.lock`.
6. **`packages/core/package.json` dev dependency.**

### The consequence #272 must absorb

That sixth edit is a **core-to-pack dependency edge**, which is exactly what
Design Problem 8 says nothing currently forbids. It is dev-only and confined to
the test surface, and case 7 holds the rest of core to the ban by asserting that
no file under `packages/core/src` imports the pack.

**`no-domain-pack-import` (#272) must therefore be scoped to `packages/core/src`
rather than to `packages/core`.** A rule written against the package as a whole
will fail on `packages/core/test/binding-conformance.test.ts` and on the
`package.json` dependency, and the correct response would not be to weaken the
rule but to have scoped it correctly in the first place. This is flagged on #272.

The alternative — putting the suite in `packages/domain-null/test` and
self-referencing by package name — was measured and also works (Bun 1.4.0
supports self-reference through the `exports` map, and a bare root `bun test`
discovers the suite either way). It was not chosen: the human decision was
Option A, which keeps the test plan's stated command `bun test packages/core`
correct for all three cases with no plan deviation.

### The survivor: a range exemption is a hole shaped like whatever fits in it

Case 14 must permit the five literals where CLAIM-31.6 allows them — the id
union. The obvious implementation, and the one already in the tree at
`binding-types.test.ts:260`, exempts every line **between** `export type
KnownDomainId` and the array's closing `];`.

Inserting `export const DEFAULT_DOMAIN: KnownDomainId = "dev";` into that gap is
a direct violation of CLAIM-31.6 — core branching on a domain literal — and it
survived **all 755 tests and `bun run lint`**. The identical line appended at
end-of-file was killed, which proves the region was the hole rather than the
regex.

Fixed by making the exemption **shape-based**: a hit qualifies only if it is the
union declaration line itself or a bare array element matching
`/^"(dev|trade|health|wealth|know)",?$/`. The count is additionally **pinned at
6** (union + five elements) so a sixth exempted line cannot appear unexamined —
the technique case 7 already used and case 14 did not. Re-running the mutation
against the fixed suite kills it.

> **An exemption expressed as a line range admits anything that fits inside the
> range.** Express it as a shape, and pin the count.

### A second survivor, recorded not fixed

`maskComments` is not string-aware: it blanks everything after the first `//` on
a line, so `const u = "https://example.com/nullBinding";` is real code that
scans clean and survives both case 7 and case 14. This is inherited from
`scripts/lint.ts:36` and is a repository-wide property rather than something
these tests introduce, so fixing it here would fix one of its several call
sites and leave the rest. Recorded as a finding.

## Two vacuous assertions, caught before they shipped

Case 6 asserts its own import is by package name, so that rewriting it to a
relative path fails rather than quietly stopping proving anything. The first two
attempts were both wrong, and both are the classes this Story keeps meeting:

1. A substring check over the raw source failed on **this file's own
   commentary**, which discusses the relative form in prose. Third documented
   instance of the prose-versus-code trap in this repository.
2. Masking comments was not enough. `expect(self).toContain('from "iai-domain-null"')`
   **puts the string it searches for into the code it searches**, so it passes
   with the import deleted. A condition that cannot fail is an assertion that
   does not exist.

Both are fixed by matching parsed `from "<specifier>"` occurrences: an
assertion's own argument is never preceded by `from`. Mutation 11 confirms the
result is live.
