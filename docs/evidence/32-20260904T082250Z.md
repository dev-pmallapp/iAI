## A name collision, found by the compiler rather than by review

`bun run typecheck` failed on the first build of the barrel:

```
packages/core/src/index.ts(6,1): error TS2308: Module "./guards/index" has
already exported a member named 'Rung'.
```

**`Rung` is declared twice in this package.**
`packages/core/src/guards/risk-mandate.ts:13` has had
`type Rung = "research" | "paper" | "live"` since S1.2 — a rung *identifier*.
`packages/core/src/binding/domain.ts:142` declares the `Rung` of
`docs/design/01-skill-hierarchy.md:203-209` — a rung *definition object*, and
one of the seven types `CLAIM-31.1` binds this task to by name. Different
things, same word.

Resolved by explicit re-export at the root barrel, which beats `export *`, so
`Rung` at the package root means the contract type and the older one stays
reachable as `RiskMandateRung`. Nothing breaks: **no file outside `guards/`
imports the older one**, verified by search before the alias was written.
Renaming either declaration was rejected — one would edit `CLAIM-31.1`'s
vocabulary, the other S1.2's shipped surface.

This is the same hazard `packages/core/src/evidence/index.ts:31-34` documented
for `safeOwnValue`/`safeOwnString`, and the Design anticipated it for `DomainId`
while missing it for `Rung`. **`export *` at the root barrel makes every new
directory a collision risk with four existing ones**, and TS2308 is the only
thing that finds it — a compile error rather than a silent last-one-wins, which
is the good outcome.

## Two assertions that were wrong before they were right

**The compiler emits TS2820, not TS2322, for the closed union**, and the
difference is worth keeping. TS2820 is the *"did you mean"* diagnostic tsc
produces only for a closed string-literal union:

```
error TS2820: Type '"helth"' is not assignable to type 'KnownDomainId'.
Did you mean '"health"'?
```

Decision 1 claims that opening `DomainId` leaves an editor still completing the
five. Asserting the suggestion proves that property **directly**, where the
plain assignability error this case was first written to expect would only have
proved the assignment failed.

**The `evidenceRequired` diagnostic names the types, not the field.** The first
assertion looked for the string `evidenceRequired` and would have passed on any
TS2322 anywhere in the fixture — the same over-broad matching the two-run
directive harness exists to prevent. It now asserts
`Type 'false' is not assignable to type 'true'`.
