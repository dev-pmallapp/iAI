## What was actually unenforced

`isPureModulePath` matched only the path segments `classify` and `guards`. Any
file under `packages/core/src/gh` could `import "node:child_process"`, call
`Bun.$` and call `fetch(` and produce **zero** violations.

Every module #22 through #25 landed was written to be pure and was verified by
hand at each task, but `CLAIM-21.1` — "no file under `packages/core/src/gh`
references `child_process`, `Bun.$` or `fetch`" — was a claim with no
enforcement behind it for the whole of S1.3.

**No new rule was needed.** `CLAIM-21.1`'s three banned tokens map one-for-one
onto detections the rule already implements: `IO_MODULE_SPECIFIERS` covers both
spellings of `child_process`, `BUN_MEMBER_RE` covers `Bun.$`, and
`FETCH_CALL_RE` covers `fetch(`. This is a scope widening at three sites — the
predicate, the comment naming its authority (`CLAIM-15.6` was no longer the only
one), and the printed `RULE_SCOPES` string, which is the user-visible contract.

## Case 20 — the mutation test, and why three cases and not one

Cases 18 and 19 prove the directory is in scope and is exercised. **Neither
proves the rule fires.**

That distinction is not hypothetical in this repository. `skill-lint` runs in
CI, reports success on every run, and scans **zero files**, because `skills/` is
empty. A purity rule that silently matched nothing would be the same failure
with far worse consequences: it would report green while the kernel shelled out.

Five mutations were introduced under `core/src/gh` and each was required to be

## The vacuous pass this task nearly shipped

Case 2's first implementation called `lintTree(join(repoRoot, "packages", "core", "src", "gh"))`.

`lintTree` expects a directory whose **children are packages**: it reads
subdirectories, treats each as a package, and walks source files inside them.
`packages/core/src/gh` has no subdirectories — every module is a flat `.ts`
file. So the loop body never executed, the function returned `[]`, and the
assertion passed **having scanned nothing**.

It was green for the wrong reason, in the very case written to prevent
green-for-the-wrong-reason.

It now lints each real file individually and asserts
`files.length >= 8` first, so if the directory is ever emptied or moved the test
fails instead of silently proving nothing. It currently scans **12** files.

## Case 2's verifier is deliberately not a substring grep

`docs/test-plans/21-plan.md` specifies case 2 as "`grep` over the directory ...
0 occurrences of all three tokens". A naive substring grep is wrong, and this
Story tripped it three separate times on **correct** code:

| Where | Token | Why a substring match is wrong |
|---|---|---|
| `gh/types.ts` (#22) | "fetched" | prose in a comment, not a `fetch(` call |
| `gh/errors.ts` (#25) | a verbatim quote of `docs/design/09-security.md` | prose again |
| `gh/pr.ts` (#24) | `mergeCommit` | a legitimate `--json` field name, and `NEVER-21.10` checks for `merge` |

The lint rule is correct in every instance: `FETCH_CALL_RE` is `/\bfetch\s*\(/`
and `NEVER-21.10` compares argv elements with `===`. So case 2 is asserted
through the real rule against **call forms**, and a companion test proves the
distinction directly — prose containing the word is not a violation, a call is.

Three false positives in one Story is enough evidence that the plan's stated
verifier, not the code, was the thing that needed correcting.

## The scope predicate still matches segments, not substrings

Widening a scope is exactly when an accidental substring match becomes
dangerous. A test asserts that `core/src/ghost/` and `core/src/guardsomething/`
stay **out** of scope, so the `gh` alternative cannot quietly pull unrelated
directories into a rule that forbids I/O.

## Case 19 — exercised, not merely in scope

The stubbed-runtime harness previously imported only the `classify` and `guards`
barrels, so it would not have caught I/O on a `gh` code path. It now exercises
one constructor per family named by `CLAIM-21.1`, plus `classifyExitCode` and
`planLabelTransition` from the response side, with `fs`, `net` and `process`
armed to throw.

A constructor that never runs proves nothing about a parser that does, which is
why the response-side functions are included rather than the argv builders
alone.
