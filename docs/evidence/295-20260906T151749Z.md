## The mechanism is the point, not the two rules

The sentence was false since S2.1. It survived because **nothing cross-checked
the document against the linter it describes** — `skills/` is outside
`claim-lint`'s scope, which is #296's subject.

The first mechanism considered was to name each capability's rule id inline in
the prose and assert that every *named* id resolves. **That mechanism cannot see
the defect at HEAD.** Run it against `:128-129`: the false sentence carries no
marker, so it resolves nothing, matches nothing, and passes. It detects only the
narrower "a marker names a typo'd id", and the next contributor who writes
"Also checks: frontmatter key ordering" reproduces the defect verbatim against a
green suite.

**Set equality over a complete table closes the class instead of the instance.**
A capability that is not a rule has nowhere to live except a row whose id fails
membership. Prose outside the table is declared non-normative in the document
itself.

## Detection is deliberately narrow

A section rule fires on **absence**, which makes it **exemption-shaped**: a
match that succeeds too easily does not become noisy, it silently stops asking
for the section. That is the dangerous direction, recorded three times already
in this repo.

| Property | Shape | Pinned by |
|---|---|---|
| H2 only | `^## ` anchored, `m` flag | `### Phase 0` fails — M3 |
| Case-sensitive | no `i` flag | `## phase 0` fails |
| Suffix allowed | no `$` anchor | `## Phase 0: Context Discovery` passes |
| Longer number excluded | `(?![0-9])` | `## Phase 01` fails — M2 |
| Longer word excluded | `\b` | `## Error Handlingz` fails — **M8** |
| Fenced code is not content | `stripFencedCode` first | a heading inside a ``` fence fails — M1 |

The `(?![0-9])` is the same shape and rationale as `routingForms`'
`(?![a-z0-9])`, whose header comment explains the identical problem for domain
ids.

**Fence-stripping was added before the first run, not after a failure.** A skill
body that *shows* an example skeleton in a fence is the expected shape for these
four verbs, so the heading would have appeared inside a fence in the very first
real corpus. Same posture as `packages/core/src/guards/claim-lint.ts`'s `inFence`
toggle; reimplemented locally rather than imported, because that module's
fence-skip is woven into a structural parse this rule has no other need for, and
importing it would couple this rule's population to `claim-lint`'s.

## A review catch that mutation testing would not have found

Gating the two rules on `isSkill` broke **20 pre-existing tests**, because
unlike every prior body rule — which fires on the **presence** of something bad
— these fire on the **absence** of a heading, so every tiny fixture written for
an earlier rule began tripping them.

The first repair flipped 12 of those call sites to an explicit
`{ isSkill: false }`. **That is a silent weakening.** `lintBodyRules`'s
`options` defaults to `{ isSkill: true }`, so those tests had been running
against the **skill** population; the flip moved them to the contract
population while leaving their `skills/.../SKILL.md` fixture paths in place — a
combination `lintSkillTree` can never produce, since it always passes
`isSkill: true` for a `skills/` path. Several of them are the standing evidence
for `CLAIM-41.6` / `NEVER-41.7`, which are claims **about skill bodies**.

Corrected by appending a `REQUIRED_SECTIONS_SUFFIX` to each fixture body and
restoring the default population, which preserves each test's original meaning
exactly. **No mutation of the source would have revealed this** — the tests
passed, and they tested the wrong population. It was found by reading the diff
and asking why a `skills/` path was being linted as a contract document.
