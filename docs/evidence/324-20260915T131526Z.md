## Case 15, and the finding underneath it

The egress gate runs **first** in `live-rung init`, before anything touches the
filesystem, and demonstrates its converse on the same path: if a `USER/`-derived
payload is not refused, `init` fails. A gate that cannot be shown refusing is an
unexercised branch. Observed on the live path:

```
egress gate ADMITTED the declared-synthetic goals fixture (class INTERNAL, destination cloud)
egress gate correctly REFUSED a USER/-derived payload (class PRIVATE)
```

**The finding, now #336.** `packages/core/src/classify/classify.ts` imports only
`./levels` and `./recognisers` — it never imports `./path`, so `classifyPath`'s
`USER/` rule is consulted by nothing. Measured:

| payload | `classify()` |
|---|---|
| `{ source_path: "USER/HEALTH/labs.yaml", … }` | `PRIVATE` |
| `{ zzz_unrelated: "x" }` — no `USER/` anywhere | `PRIVATE` |
| `{ work_state: "USER/HEALTH/labs.yaml" }` | **`INTERNAL`** |
| `classifyPath("USER/HEALTH/labs.yaml")` | `PRIVATE` |

Row 3 is the hole. Row 2 is why it went unnoticed: a test using a `USER/`-ish
payload with unrecognised keys passes **whether or not the rule is wired in** —
it cannot distinguish the reason for its own answer.

**Case 15 still passes honestly.** Its wording is *"`USER/`-derived content is
`PRIVATE` **by fail-safe default**"* — the unrecognised-key rule, which is
exactly what fires. The test now says so in its own name, a control proves the
discrimination, and a tripwire asserts `classify.ts` does not import `./path`,
so wiring it in forces this record to be revisited deliberately.

**`NEVER-293.10` holds:** the gap is in **classification**, not in the guard.
The guard blocks everything it classifies `PRIVATE`.

**And the gate is not what protects this command.** A real goals document under

`renderGoalsFixture` with no flag, argument or code path that can redirect it —
asserted by test. Two protections guarding two different things; conflating them
would leave a hole nobody is watching.

## Why the live rung can never become required

`.github/workflows/live.yml` is a **separate file** with `workflow_dispatch` as
its only trigger. The separation is the mechanism, not tidiness:

- a job in `ci.yml` runs on every `pull_request`, and a live job must not;
- `ci.yml` deliberately carries no `paths:` and no `branches:` filter, because
  NEVER-9.8 says a filtered workflow leaves required checks pending forever — so
  there is no way to add a non-PR-triggering job to that file;
- a `workflow_dispatch`-only workflow cannot fire on a PR, which is also why it
  can never be accidentally promoted: a context that never reports would block
  every PR forever if required;
- fork PRs receive no secrets — Problem 7a's third independent reason.

The job proves the seam (`live-rung --help` and its test file) and never opens a
session against a real repository.

`test/ci-workflow.test.ts` asserts the count **before and after** by reading it,
never by hardcoding `6` — so **#334** taking it to seven will not require editing
this test to keep it true. The partition now spans **both** workflow files: every
job in every workflow must be required, or named not-required with a reason.
