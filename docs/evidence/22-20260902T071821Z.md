## The hostile corpus found a real defect, and it was fixed in the code

The first implementation read `input.title` directly. A fixture carrying a
throwing getter on `title` propagated the exception straight out of
`issueCreate` — precisely what `NEVER-21.8` forbids.

Every object-taking constructor now snapshots each field through
`safeOwnValue` **before** validating any of it. That is the same shape
`guards/egress.ts` uses for `Destination`, and it matters because it does not
depend on anyone remembering to use a safe reader when a future field is added.

The test was not weakened to accommodate the bug. A second failure in the same
run *was* a test defect — an argv length asserted as 7 when the correct value is
8 — and that one was corrected in the test.

## Decision 2, and why CLAIM-21.3's literal reading was not implemented

`CLAIM-21.3` says "exactly one `gh issue edit` carrying **both** `--add-label`
and `--remove-label`". `docs/design/03-workflow.md:224` says the opposite for a
real case: "For an issue entering its first status, the `--remove-label` is
simply omitted."

The invariant the workflow document is protecting is stated at
`docs/design/03-workflow.md:167-169` — "so there is no window where the issue
has zero or two statuses". That is **atomicity**, not flag count. Emitting a
`--remove-label` for a label that is not present would be a fabricated argument
standing in for an honest absence.

| Situation | Commands | Flags |
|---|---|---|
| predecessor present | 1 | `--add-label` + `--remove-label` |
| first status | 1 | `--add-label` alone |
| already applied | 0 | — (success) |

Case 8 drives a nine-input corpus and asserts no result is ever length 2.

## Exclusivity is derived only where the tree states it

`status:`, `domain:` and `rung:` carry an at-most-one or exactly-one rule
(`docs/design/03-workflow.md:150-152`, `:165`). `gate:*`, `risk:*`, `class:*`
and `iai` are called "additive markers ... orthogonal and may coexist" at
`:153`, so this module does **not** invent an exclusivity rule for them — a
caller wanting `gate:pending` swapped for `gate:approved` passes an explicit
`remove`, which makes it a choice at the call site rather than a policy the
module made up.

A test asserts the negative case directly: `gate:approved` over `gate:pending`
with no explicit `remove` emits **no** `--remove-label`.

## A corrupted issue is refused, not half-fixed

Two labels from one exclusive family is the corruption
`docs/design/03-workflow.md:165-166` says warrants a hard failure. This layer
cannot emit that block, so it returns a typed failure naming both incumbents
rather than removing one and leaving the other — which would look like it
worked.
