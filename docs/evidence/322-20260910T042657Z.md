## The thirteen denominators, and the two that are not among them

Every one is decided by `decideVerdict`, a pure function over typed
observations, and each is reported on its own line whether it passed or failed:

1 skills on disk `> 0` · 2 covered skills equal skills on disk, **as sorted
lists** · 3 skill count equals `PINNED_SKILL_COUNT` · 4 roster non-empty ·
5 scenarios executed equals roster length · 6 **every skill has ≥ 1 scenario,
per skill** · 7 every skill has ≥ 1 Re-entry row · 8 seed tree hashes distinct
by **cardinality** · 9 a real `.git` per scenario · 10 `run1.mutations > 0`
**before run 2 is executed** · 11 `run2.mutations == 0` with the argv reported
**as the list** · 12 `run2.reads >=` that skill's row count · 13
`run2.treeHash == run1.treeHash`.

Two further checks are deliberately **not** counted among the thirteen and are
labelled as such in the source: read-attribution validity, and a named
`unclassified-argv` population. The second is a partition rather than a
carve-out — an argv that fits no kind fails loudly instead of being ignored.

### Three mutations survived their first run and are now killed — those are the findings

**M10, M11 and M12 all survived the first pass.** Each was a real gap, each was
closed, and each was re-run to confirm the kill. They are recorded here because
what they found is more useful than the fact that the suite is now green:

- **M10 killed the process instead of reporting.** A fresh forge before run 2
  made a transcription throw on an empty read, and the runner died with an
  unhandled rejection — **no verdict, no artifact, no scenario named**, exactly
  when the artifact is most wanted. A harness whose failure mode is a crash
  cannot say which scenario failed. Fixed with a `scenario-threw` failure code:
  a throw is now a recorded failure naming the scenario and the run index, and
  `decideVerdict` emits **one** failure for it rather than doubling it with a
  vacuity failure for the same cause.
- **M11 was behaviourally equivalent, so no dynamic test could ever kill it.**
  Deriving the exit code from `renderReport(...).includes("verdict: pass")`
  produces the identical answer for every fixture in the corpus. The check had
  to be **static**: `decideVerdict`'s own source may not contain `renderReport`,
  `renderArtifact`, `SUCCESS_PHRASES`, `.includes("` or `stdout`, with the
  extracted body length asserted non-zero first so a failed extraction cannot
  pass vacuously. This is finding 37 — a harness that decided on a substring of
  its own output — and its recorded owner was *any future harness*.
- **M12 exposed an unasserted field.** `renderArtifact` could emit
  `verdict: "pass"` on a failing run and every test passed, because the only
  agreement assertion compared exit codes and the real roster never fails. The
  artifact is what **#323's CI job will read**, so an artifact disagreeing with
  its own process is a green job over a red run. Now asserted in both
  directions, on a passing **and** a failing verdict.

## Findings

### 1. #321's write-seam lint was red against correct code, and the repository had already recorded the class

`packages/harness/test/mutation-recorder.test.ts`'s sanctioned-writer list
matched the **bare words** `writeFile`, `mkdirSync` and the rest anywhere in a
module's source. `runner.ts` exposes a `writeFile(relPath, contents)` on its
scenario context that does nothing but delegate to `recorder.writeFile`, and
imports no filesystem module at all — and the lint scored it as a fourth
writer.

The repository had already learned this exact lesson in the other direction:
`packages/exec/test/port.test.ts` rewrote its launcher detector from a call
shape to an **import** after `RegExp.prototype.exec(` false-positived, and the
standing rule is that for an *assertion* — unlike a ban — a false positive is
red against correct code and must be fixed. **The class was known, written
down, and reproduced one task later anyway.** The detector now reads the
capability off the import list, and a regression test asserts that a module
containing the literal text `writeFile` while importing nothing from `node:fs`
is a non-writer.

### 2. The read count may not be computed by subtraction, and this is measured

`isMutatingGhArgv` returns `false` for **every** `git` argv by construction, so
`calls.length - attemptedMutations.length` scores `git add` and `git commit` as
reads. A run 2 that committed four times and read nothing would satisfy
`reads >= 4`. `classifyArgv` is therefore a **positive** classifier over five
named kinds with `unclassified` as a counted population, and M5 is the
measurement: the subtraction passes the real roster and dies only to a
deliberately mixed roster containing both `git` writes and `gh` reads.

### 3. The fake forge models neither a milestone `PATCH` nor `--milestone` on `gh issue edit`

Two `## Re-entry` branches are therefore **dead in this roster**:
`goal-create`'s amend-the-description branch and `story-create`'s
assign-to-milestone branch. Both are dead for a *correct* reason — run 1
creates the milestone with its description already right, and creates each
Story with `--milestone` — so no scenario can reach them honestly. They were
left implemented and unexercised rather than deleted or forced: a scenario
built to reach them would have to be built around the fake's gaps, which is the
fake tuning the test rather than the test exercising the skill. **The gaps are
recorded here and belong to #323's audit and #324's live rung.**

### 4. The verdict has no fourth place to hide

The exit code is a field on a value returned by one pure function; `MutationReport`
carries no stdout at all, so the verdict is **structurally incapable** of
depending on one; the wrapper passes `verdict.exitCode` to `process.exit`
without a branch; and a static assertion pins `decideVerdict`'s source. Case 22
seeds the runner's own success phrases into a fixture that must still fail
(direction A) **and** the failure vocabulary into a fixture that must still
pass (direction B) — direction A alone would be satisfied by a runner that
inverted a grep.
