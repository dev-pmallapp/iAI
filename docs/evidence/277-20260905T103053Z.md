## The defect

The reviewed allow-list at `packages/core/src/guards/path-allowlist.ts` exempts a
repo-relative path from `claim-lint`'s `path-dangling` rule, for paths cited in
docs but absent from the tree. **Nothing removed an entry when the path came
into existence**, so the list only ever grew.

Measured on `main` @ `5748e1d`: **6 of 43 entries named paths that now exist**,
all `reason: "planned"`, five of them created by S1.1, S1.3, S1.4 and S1.5.1-2
without the entry being retired.

**This is a fail-closed concern, not tidiness.** `path-dangling` stops checking a
citation once its target is allow-listed. A stale entry is therefore a permanent
hole: if the path is later deleted or renamed, every citation to it goes
unchecked, because the allow-list still forgives it.

Every Story that created one of those paths had a defensible reason not to touch
a reviewed list belonging to another guard. That is precisely why the fix is a
**guard** rather than a cleanup — the cleanup had no owner, and the guard gives
it one automatically.

## What was built

`staleAllowListEntries(knownPaths)` in `guards/path-refs.ts`, **pure**: existence
is *supplied* via the `knownPaths` set that module already receives, so its
header claim that it "cannot check whether a path exists" remains true.

`scripts/claim-lint.ts` wires it up as `allowlist-stale`, resolving line numbers
by reading the allow-list source — the I/O stays in the script. It reuses the
**same** `knownPaths` set `path-dangling` was already given, so the two rules
cannot disagree about what exists and the guard costs no extra filesystem work.

**The rule is uniform across every reason**, not special-cased to `planned`. All
six real cases were `planned`, but `fiction` asserts the path will *never* exist,
which makes a fiction entry whose path exists the sharper contradiction.

## The counts were prose, and wrong

The header said **"Six families, 38 entries"** against **43 entries across 7
sections** — drifting quietly for three milestones because nothing read it. The
total, the family count and each per-family count are now parsed and asserted.
`packages/**` said 9 while holding 3 after the retirements.

## It incidentally discharged #34's recorded deviation

matches" — because two genuine mentions of `packages/domain-null` sat in the

## Findings recorded, not fixed

1. **`buildKnownPaths` supplies directory prefixes as well as files**, which is
   why a directory entry like `packages/core/src/binding` matches without a
   trailing slash. Relied upon, and asserted indirectly by the real-repo case.
2. **The guard cannot see a path that exists but is gitignored.** `knownPaths` is
   built from `git ls-files` plus prefixes, so an allow-listed path that exists
   only as an ignored artifact stays unreported. No current entry is affected.
3. **`external` entries can never be reported** — they are absolute or
   out-of-tree, so they never appear in `knownPaths`. Kept in scope anyway so the
   rule has no per-reason exceptions to drift.
