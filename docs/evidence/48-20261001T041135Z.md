## Bullet 3: the merge was a skip wearing a comment that said "MERGED"

`#315` shipped `withTasksChecklist` (`packages/core/src/gh/sub-issues.ts:256`)
one task earlier, precisely so a Story body's load-bearing prose survives a
checklist update. #48's own Done-when says the checklist *"**merges** into the

The merger was wired into both capability paths and the skill body named it. But
the harness transcription — the artifact that claims to execute the body's
re-entry contract — did this:

```ts
if (!storyBody.includes("## Tasks")) {
  await ctx.port.run([... "--body", `${storyBody}\n\n## Tasks\n\n...`]);

```

It **never called `withTasksChecklist`**, and when the section already existed it
wrote **nothing at all** — under a comment stating the checklist was *"MERGED
into it"* and crediting #315. A test, `"a body that already has ## Tasks is not
rewritten at all"`, pinned the skip as intended behaviour.

**Skipping is not merging, and the body names the exact case that breaks.** Its

table."* On that re-run the new row's task issue **is** opened — the create step
keys on title — and then the body step sees `## Tasks` present and returns. The
checklist never gains the entry. Not on that run, and not on any run after it.

Both branches now go through `withTasksChecklist`, its refusal path is a hard
failure rather than a guess, and the write is guarded so a merge that reproduces
the body it read issues no call at all — which is what keeps the harness's
`run-2-mutated` invariant honest rather than merely green.

## Bullet 5: the one mutating step with no read in front of it

Parenting a task is a mutation, and which of its two paths runs is decided by a
**read** — `subIssueCapabilityProbe` (`packages/core/src/gh/sub-issues.ts:63-80`).
`SKILL.md` said `sub-issues.ts` *"owns both paths and the choice between them"*
and then never mentioned the probe: no Phase 0 item, no `## Re-entry` row, and
the strings `capability` and `probe` did not occur in the file. The transcription
hardcoded `--body "Parent: #N"` and never probed at all.

That read is not a formality. `sub-issues.ts:15-27` records the incident:

> *Observed directly on 2026-09-01 against dev-pmallapp/iAI: a `subIssues` query
> on #243 returned empty and read as though the fallback path was in use, when
> all three of its tasks were real sub-issues.*

Without `-H "GraphQL-Features: sub_issues"` the API returns no nodes **and no
error** — byte-for-byte identical to an instance with no sub-issue API. The
module calls it *"the most dangerous failure this module can have."*

### The fake forge had to answer, and `unmodelled` is not an answer

The obvious implementation — read the probe, treat a non-zero exit as `absent` —
is the bug itself. `packages/harness/src/fake-forge.ts:371-383` documents its
unmodelled response as *"a gap in the double, never a forge refusal"*, exit-coded
so it *"can never be read as either a refusal or a rejection."* Reading it as
`absent` would have made the degraded path permanent and silent inside the very
harness built to catch that.

So the probe is **genuinely modelled**. The fake answers a definite `present` or
`absent`, and **it honours the feature header the way the real API does**: the
same probe sent without `SUB_ISSUE_FEATURE_HEADER` answers `absent` even on a
fake configured `present` (`fake-forge.ts:537`, `:547`). The 2026-09-01 hazard is
now a test, not a comment.

`## Re-entry` gained row 3 and the transcription gained `ctx.read(3, probeArgv)`
before the create loop; the old rows 3/4/5 renumbered to 4/5/6. Both paths are
