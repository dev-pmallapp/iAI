## Six findings

### 1. Case 8 asserted on an exit code cannot detect an enforcing fake

Recorded above as M9/M9b. Generalises to every test of a permissive double: a
double that refuses and a double that accepts return the same verdict on the
**first** call, and differ only in state on the second. **Owner: pattern —
applies to #321, #322 and #323, all of which will assert against this fake.**

### 2. Exit code and row counts collapse **three of the five** failure modes

Measured while writing `case 9 (i)`. On `read.exit` + `read.rows` +
`create.exit` + `state.rows` the five modes produce **three** distinct
signatures: the zeroed budget, the header-absent 403 and the transient error are
all *"the read exited 1 and returned no rows"*. Adding `classifyRateLimit`'s
answer to the signature separates all five.

This is not a defect in the fake. It is the measurement that justifies case 20
existing at all: **the five lies are not distinguishable by what they do, only
by why.** A harness branching on the verdict would treat a rate limit, a
permission failure and a dropped connection as one event.

### 3. `shouldRetryResponse` answers `retry: false` for a transient connection error

Measured directly:

```
classifyExitCode(1)   -> { code: 1, classification: "fatal", provenance: "observed" }
classifyRateLimit(..) -> "not-rate-limited"
shouldRetryResponse   -> { retry: false, reason: 'exit code 1 classifies fatal (observed) and
                                                  rate limit classification is "not-rate-limited"' }
```

`references/gh-error-handling.md:120-131` records **three** `gh` calls failing
with a connection error in a single session, **each succeeding on immediate
retry**, and instructs *"Retry once before believing a failure."* The kernel's
own retry-decision function does not retry the failure mode the reference
document exists to tell you to retry. **Needs an issue — not yet raised.**

### 4. The kernel's own `reason` strings differ only in the value they quote

`packages/core/src/gh/errors.ts:270` returns
`rate limit classification is "rate-limited"` and, for the third state,
`...is "possibly-rate-limited"`. Two messages that differ only in the value they
quote are one message — `references/verification.md:127-129`, the rule this
repository has now paid for three times.

It is inside the kernel, in a `reason` field whose purpose is to be read by a
human deciding why a batch stopped. **This is why none of case 20's distinctness
assertions use that string**; they assert the classification **value** and the
**absence** of the other two. Recorded, not fixed: changing a kernel message is
not this task's. **Owner: whoever next edits `errors.ts`.**

### 5. `git clean -fd` destroyed this task's uncommitted work, and the handoff recommends it

The handoff records that `rm` is denied by tool policy and directs the reader to
`git clean -fd` instead. **`-fd` removes untracked files, and a task in progress
before its first commit consists entirely of untracked files.** Both new files
were destroyed by a cleanup of a stray probe script and had to be rewritten.

The recommended remedy is not the recommended verb. **Commit before any cleanup
verb, or use `git stash -u`**, which is recoverable. This is the same class as
the handoff's existing warning that `git checkout <file>` reverts to the index —
a recovery verb that destroys the thing being recovered. **Owner: the handoff.**

### 6. The `## Re-entry` column yields 16 keys, not the 4 the plan names

Recorded under *Case 8* above. The plan's four are read as classes. The fifth
literal key — `docs/test-plans/{n}-plan.md` — is honestly classified
`worktree-path` rather than pretended away.
