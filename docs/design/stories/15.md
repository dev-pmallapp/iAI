# S1.2 — Data classification and the guard kernel

**Story:** #15 · **Milestone:** M1 — Kernel and foundation
**Unit of work:** one pure module
**Widens:** `packages/core/src/decision.ts`, `packages/adapter-claude/src/index.ts`,
`packages/adapter-opencode/src/index.ts`

This Story lands the egress block before any health, wealth or trade code exists.
That ordering is the entire reason it sits second in M1, and it means the four
guard predicates are being written against design documents rather than against
callers. Where those documents disagree with each other — and on this subject
they disagree in nine places — this Design picks one reading and records why.

---

## Problem

`docs/design/09-security.md` is the only full statement of the classification
model, and it is the most internally inconsistent document in the tree. Three of
its contradictions are load-bearing for S1.2's acceptance criteria, which means
they cannot be deferred to a later reconciliation pass the way #14's findings
were.

**1. The published `checkEgress` signature cannot satisfy its own claim.**
`docs/design/09-security.md:105-108` gives a two-parameter signature. Eleven
lines later, `docs/design/09-security.md:125-126` states that the guard
"receives a snapshot of session consent state; it does not go and look one up".
There is no parameter for it to arrive in, and `Destination`
(`docs/design/09-security.md:110-114`) has only `vendor`, `locality` and
`region?`. CLAIM-15.4 requires the guard to branch on that consent.

**2. The destination policy matrix does not exist.** `docs/milestones/M1.md:106`
names it as a build target and `docs/milestones/M1.md:111-113` requires a
hostile-input fixture set to drive "every branch of the policy matrix" and
return "the documented action". No class-by-destination table exists anywhere in
the repository. What exists is four prose cells at
`docs/design/09-security.md:49-52`, two absolutes at
`docs/design/09-security.md:56-63`, and the phrase "Allow, redact-then-allow, or
block" at `docs/design/09-security.md:100`. Separately, `warn` is a member of
`Action` (`packages/core/src/decision.ts:9`) that no rule anywhere produces.

**3. The `Decision` shape is published in two widths.** The milestone's own
feature row (`docs/milestones/M1.md:21`), `ARCHITECTURE.md:141-142` and
`docs/design/08-dual-target.md:91-93` all say `Decision { action, message }`, and
that two-field form is what S1.1 shipped at `packages/core/src/decision.ts:11-14`.
CLAIM-15.3 and CLAIM-15.4 both require the three-field form at
`docs/design/09-security.md:116-120`, and neither shipped adapter reads a
`redacted` field at all.

Beneath those three sit a further six: whether opted-in PRIVATE data may reach a
cloud vendor at all, whether `locality` means anything for SECRET, whether the
50 ms budget is a p99 or an always, and three scope questions where S1.2's task
list overlaps work already shipped in S1.1 or scheduled for M6 and M7. Each is
adjudicated below.

## Vision

Four predicates and one classifier exist exactly once, in
`packages/core/src/guards/` and `packages/core/src/classify/`, as pure functions
over caller-supplied snapshots. Both hosts block by translating the same object.
The class-by-destination matrix is written down, every branch of it has a
hostile-input fixture, and a reader can determine from the matrix alone what any
payload does against any destination without reading the implementation.

## Constraints

- **No I/O, at all.** Not the "one small `readFileSync`" that
  `docs/design/08-dual-target.md:215` permits a guard in general. CLAIM-15.6
  binds `classify/` and `guards/` to a stubbed-runtime harness where `fs`, `net`
  and `process` throw, so the permitted read is unavailable to these modules
  specifically. This follows the precedent already set in-tree at
  `packages/core/src/guards/claim-lint.ts` and
  `packages/core/src/guards/path-refs.ts`: guards take strings and snapshots and
  return data, and the file-walking shim lives in `scripts/`.
- **Fail closed on absence.** An omitted consent argument, an unrecognised class
  and an unrecognised destination each deny. There is no code path in which a
  missing input widens permission.
- **The two-field `Decision` stays assignable.** S1.3, S1.4 and S1.5 import this
  type (`docs/milestones/M1.md:261-271`). Any widening must be additive, so that
  code written against the shipped shape keeps compiling.
- **`process.cwd()` is banned and lint already enforces it** for `packages/core`
  and `packages/adapter-opencode` (`scripts/lint.ts`). A guard resolving `USER/`
  against the wrong tree fails open, which
  `docs/design/08-dual-target.md:197-203` names as the specific hazard.
- **No safety guarantee may depend on an opencode-only capability**
  (`docs/design/08-dual-target.md:509-513`). Every block in this Story must be
  expressible through `PreToolUse` exit 2 as well as through a throw.

## Goal

A payload cannot reach a destination it is not classified for, the rule that
decided so is readable as a table rather than as code, and the guard that
enforced it did no I/O to reach its verdict.

### Decision 1 — the consent snapshot is a third parameter

Three shapes were available and all three depart from the verbatim signature at
`docs/design/09-security.md:105-108`, because that signature has nowhere to put a
value the same document insists the guard receives.

Putting consent on `Destination` was rejected: it conflates where a payload is
going with what the principal permitted, and it would make a `Destination`
constructed in a test carry authority. Wrapping both arguments in a context
object was rejected: it invalidates every two-argument call site cited across the
design tree for a purely cosmetic gain. A third parameter is additive, leaves
`Destination` honest, and leaves the first two arguments exactly as published.

The parameter defaults to withheld. A caller who forgets it gets a denial, not an
allowance — which is the whole point of NEVER-15.8, and the reason the default is
in the signature rather than in the caller's discretion. The snapshot is a value
handed in, never a lookup: `docs/design/09-security.md:125-126` and
`docs/milestones/M5.md:226-227` both require this, and CLAIM-15.6 makes it
structural, since a lookup would need I/O the harness forbids. It also delivers
`docs/milestones/M5.md:213-214` for free: a guard that cannot read a config layer
cannot be enabled from one.

### Decision 3 — the matrix, and the absent `warn`

| Payload class | `locality: "on-device"` | `locality: "cloud"`, consent withheld | `locality: "cloud"`, consent granted |
|---|---|---|---|
| `PUBLIC` | `allow` | `allow` | `allow` |
| `INTERNAL` | `allow` | `allow` | `allow` |
| `PRIVATE` | `allow` | `block` | `allow` + `redacted` |
| `SECRET` | `block` | `block` | `block` |

Every cell is derived, not invented. The `PUBLIC` and `INTERNAL` rows are
`docs/design/09-security.md:49-50`. The `SECRET` row is
`docs/design/09-security.md:52` widened by `docs/design/09-security.md:56-58` per
Decision 5. `PRIVATE` on-device is the posture the rest of the tree assumes when
it says private work routes to a local model. `PRIVATE` to cloud with consent
withheld is `docs/design/03-workflow.md:246`, "deny, not ask". `PRIVATE` to cloud
with consent granted is `docs/design/09-security.md:60-63`: the de-identified
projection, never the raw record, which is why that cell is `allow` + `redacted`
and not plain `allow`.

Any `locality` outside the two published values falls to `block`, per NEVER-15.8.

The matrix has four outcomes across twelve cells and `warn` is not one of them. A
warn on an egress path lets the tool call proceed and reports afterwards, which
is a leak with a receipt. `docs/design/09-security.md:73-74` already states the
governing principle — "Defaulting to the permissive class is how leaks happen" —
and a warn is that default wearing a different name.

Rather than leave `warn` reachable-but-unused, `checkEgress` returns a narrowed
type in which it does not exist:

```ts
export type EgressDecision =
  | { readonly action: "allow"; readonly message: string; readonly redacted?: unknown }
  | { readonly action: "block"; readonly message: string };
```

Both arms remain assignable to `Decision`, so neither adapter changes shape and
`toExitCode` and `applyDecision` keep taking the wider type. Narrowing is safe in
the direction of consumers; it is only the producer that loses options.

This delivers two claims structurally rather than by assertion. `warn` is gone,
which is NEVER-15.7. And `redacted` is absent from the `block` arm, so a blocked
`SECRET` payload **cannot** carry a continuation — which is the second half of
CLAIM-15.3, previously enforceable only by a test that someone could delete. A
guarantee the type system holds does not depend on a test still existing.

`Action` itself keeps `warn`, because `packages/core/src/decision.ts:9` shipped
it and guards outside this Story may legitimately want it. The narrowing is
local to egress, which is the one path where warning is indistinguishable from
failing open.

The vocabulary also needs reconciling: the flow diagram at
`docs/design/09-security.md:87-89` and the prose at
`docs/design/09-security.md:100` both name three outcomes, "allow / redact /
block", but `Action` has no `redact` member. Redaction is not a third action; it
is `allow` carrying a rewritten payload. The three-outcome prose and the
two-plus-one type describe the same behaviour and this Design treats the type as
canonical.

### Decision 4 — CLAIM-15.4 is implemented as written, and the conflict is filed

The tree holds two irreconcilable positions on whether opted-in, de-identified
PRIVATE data may reach a cloud vendor.

`docs/design/09-security.md:51`, `docs/design/09-security.md:60-63`,
`docs/design/06-domain-health.md:491` and `docs/milestones/M5.md:210-212` all say
yes, subject to a per-session opt-in and de-identification.
`docs/design/02-roles.md:387` says PRIVATE surfaces are "local-model-only", and
`docs/design/02-roles.md:580-582` says never route PRIVATE data to any cloud
vendor.

CLAIM-15.4 sits on the permissive side, and an acceptance criterion the milestone
seeded is this Story's contract. It is implemented as written.

The two readings may well be compatible — if `docs/design/02-roles.md` is read as
governing the raw record, then a de-identified projection is by construction no
longer that record, and both statements hold. But that reading is written down
nowhere, and inventing it here would be exactly the failure mode #14 was
chartered to catch. Editing `docs/design/02-roles.md` from inside this Story is
also out of bounds; it belongs to a different Story's design surface.

So it is filed as **#235** rather than resolved, following the route S1.7
established for #14's stranded findings — but filed as a standalone task with its
own home rather than as a sub-issue of a Story whose branch will be deleted,
which is the specific way those three findings got stranded. #235 must land
before M2 writes `references/data-classification.md`, which
`docs/design/01-skill-hierarchy.md:57` says owns the egress gate contract; a
reference document written over a contradiction either picks a side silently or
documents the contradiction, and both are worse than fixing it first.

Note that the strict reading is not currently implementable either:
`docs/design/verification-pass.md:153` records that "the local model" is named in
no repository, so there is no provider to route to. `checkEgress` therefore
returns a `block` whose message names the required reroute, and performs no
routing itself.

### Decision 6 — p99 is how "always" gets measured, not a weaker promise

`CONTRIBUTING.md:320` says under 50 ms "always".
`docs/design/08-dual-target.md:214`, `docs/design/09-security.md:123` and
`ARCHITECTURE.md:212` say it unqualified. CLAIM-15.5 says p99 over 10,000
iterations. `docs/milestones/M5.md:215-216` says p99 over 1,000.

These are not three different promises. "Always" is a structural property and no
benchmark can establish it — a sampled maximum is a statement about the sample,
and a garbage collection pause during iteration 8,412 says nothing about the
predicate. What actually delivers "always" is CLAIM-15.6: a function that cannot
do I/O, cannot walk a directory and cannot call the network has no unbounded
term in it, and its cost is a function of input size alone.

So the benchmark is the check and purity is the guarantee. CLAIM-15.5's p99 over
10,000 iterations is adopted as the binding gate because it is the larger of the
two published corpora. The observed maximum is reported in the evidence artifact
alongside the p99, so that a regression showing up only in the tail is visible
even though it does not fail the gate.

### Decision 7 — unknown classifies `PRIVATE`, and the weakening is recorded here

`docs/design/09-security.md:73-74` says unknown classifies `PRIVATE`.
`docs/design/verification-pass.md:993` verdicts that `corrected` against LifeOS,
which fail-closes to its *top* class, and notes that iAI's analogue of that class
is `SECRET` — so defaulting to `PRIVATE` is one level weaker. That row observes
that "the weakening is not recorded anywhere" and
`docs/design/verification-pass.md:1112` lists it as outstanding debt.

S1.2 is the Story that implements the default, so S1.2 is where the rationale
belongs, and writing it here closes the debt row at its source rather than
deferring it to another reconciliation pass.

The rationale is that `SECRET` is not a stricter version of `PRIVATE`; it is a
different contract. `PRIVATE` has an opt-in and a de-identified continuation.
`SECRET` has neither, by design — `docs/design/09-security.md:56-58` forbids
offering one. Defaulting unrecognised payloads to `SECRET` would therefore block
every unfamiliar structure against every destination, on-device included, with no
recovery path at all. That is not a stricter system; it is an unusable one, and
`docs/design/09-security.md:154-156` already names where unusable systems end up:
"a system nobody uses gets bypassed."

`PRIVATE` is the strictest default that still leaves a path forward. It blocks
the cloud, permits local work, and requires a human opt-in plus de-identification
to go further. The one-level gap against LifeOS is real, deliberate, and is the
cost of having a four-level ladder whose top rung is absolute.

**Q2 changed Decision 3 and one claim.** The proposal was to leave `warn` in the

test file it lives in.

`checkEgress` therefore returns `EgressDecision`, in which `warn` does not exist.
**This Design extends the ruling one step further than it was asked**, and the
extension is called out here so it can be reversed if it overreaches: because the
narrowed type is written as a discriminated union rather than as an interface
that merely restricts `action`, `redacted` could also be dropped from the `block`
arm at no extra cost. That makes the second half of CLAIM-15.3 — a blocked
`SECRET` payload carries no continuation — structural rather than tested. The
ruling asked for a narrower return type; taking the narrowing to both fields
follows the same reasoning to its end, and NEVER-15.7 was restated to cover both.

**Not ruled on, and not needed for this Story: whether `Action` should lose
`warn` globally.** `warn` remains in the shipped union at
`packages/core/src/decision.ts:9`, and guards outside egress may use it. The
question of whether any guard legitimately warns is live but belongs to whichever
Story first wants one. **No global narrowing is performed, and none is claimed to
have been waived.**
