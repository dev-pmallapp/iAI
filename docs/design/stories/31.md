# S1.5 — Domain binding interface and registry

**Story:** #31 · **Milestone:** M1 — Kernel and foundation
**Unit of work:** one interface or registry rule
**Creates:** `packages/core/src/binding`, `packages/domain-null`
**Widens:** `scripts/lint.ts` (purity scope, one new rule), `packages/core/src/index.ts` (barrel)
**Corrects:** `CONTRIBUTING.md` (the "Adding a domain" checklist)

The binding is the seam that lets one pipeline serve five domains. This Story
declares it, validates it, and builds the registry that turns a `domain:*` label
into one. Then it proves the seam holds by registering a binding from a package
outside `packages/core` — because an abstraction nobody has instantiated from
the outside is an abstraction nobody has tested.

---

## Problem

S1.4's difficulty was two documents specifying the same behaviour differently.
S1.5's is worse in kind: **two of its own six claims are jointly unsatisfiable
as written**, and the interface it is told to implement verbatim is missing a
type it references.

**1. `CLAIM-31.1` and `CLAIM-31.3` cannot both hold.**
`CLAIM-31.1` (`docs/milestones/M1.md:203-205`) requires the types to compile
"with every field name and type from `docs/design/01-skill-hierarchy.md`". That
file declares `id: "dev" | "trade" | "health" | "wealth" | "know"`
(`docs/design/01-skill-hierarchy.md:187`, repeated byte-identically at
`ARCHITECTURE.md:98`) — a **closed** union living inside `packages/core/src`.
`CLAIM-31.3` (`docs/milestones/M1.md:209-211`) requires that "a domain can be
registered **without editing any file under `packages/core/src`**". A sixth
domain cannot produce a conforming binding without widening a type declared in
core. Worse, `nullBinding` — mandated by `CLAIM-31.3`, `docs/milestones/M1.md:24`
and `PLAN.md:59` — **has no legal `id` at all**, because it is by definition not
one of the five. The same conflict is restated three more times downstream:
`docs/milestones/M4.md:37-38`, `docs/milestones/M5.md:82-85` and
`docs/milestones/M6.md:39-40`.

**2. The registry both must and must not be edited to add a domain.**
`CONTRIBUTING.md:303` makes it a checklist item: "Register the pack in the
binding registry (`packages/core/src/binding/registry.ts`)".
`docs/milestones/M5.md:82-85` asserts the opposite as a test: `CLAIM-111.1` is
"asserted by a test that **fails if `git diff --stat` for the story branch
touches `packages/core/src/binding`**". One names a file in the exact directory
the other forbids touching. Separately,
`docs/design/01-skill-hierarchy.md:419-421` states "**There is no separate
registry to keep in sync**" while `:59` of the same file, `ARCHITECTURE.md:92`
and `docs/design/08-dual-target.md:460` all name one.
`docs/design/verification-pass.md:244` already marks that internal contradiction
`corrected` without resolving it.

**3. The interface has six types, not four, and one of them is declared
nowhere.** `docs/milestones/M1.md:197` says "four sub-specs" and `CLAIM-31.1`
enumerates `UnitSpec`, `VerifySpec`, `GateSpec`, `EvidenceSpec`. But
`docs/design/01-skill-hierarchy.md:203-209` declares a fifth full interface,
`Rung`, and `CLAIM-31.4` reads `verify.rungs[0].reversible` — so `Rung` must
exist and must be validated. And `docs/design/01-skill-hierarchy.md:192` types
`labels` as `{ namespace: string; extra: LabelDef[] }` where **`LabelDef` is
referenced twice in the repository and declared zero times**. `CLAIM-31.1`
requires compiling every type from a file that does not contain one of them.

**4. `CLAIM-31.4`'s second half cannot fire against any conforming binding.**
`docs/design/01-skill-hierarchy.md:215` declares `evidenceRequired: true` — the
TypeScript literal type, not `boolean`. `false` is a compile error. `CLAIM-31.4`
(`docs/milestones/M1.md:212-213`) nevertheless requires the registry to reject
"a binding whose `verify.evidenceRequired` is not `true`". Read literally
against the declared type, the check is unreachable.

**5. Four fields are typed as prose and treated downstream as executable.**
`unitOfWork.minSize` / `maxSize` are `string`
(`docs/design/01-skill-hierarchy.md:198-199`) holding sentences like
`"a single entry rule with one invalidation trigger"`, yet
`docs/milestones/M2.md:206-207`, `docs/milestones/M2.md:220`,
`docs/design/01-skill-hierarchy.md:64` and `docs/milestones/M5.md:95-97` all
call them **thresholds** the binding supplies. `Rung.entryCriteria` is
`string[]` of English (`:206`) while `docs/milestones/M5.md:89-91` requires each
one to be "**evaluated as a predicate over disk state** … with that criterion
named in the message". `GateSpec.autoDeny` is `string[]` (`:223`) while
`docs/milestones/M6.md:253-256` requires each of the five conditions to
"**independently refuse** a live order … each naming its condition". A `string`
of English cannot be evaluated; it can only be asserted about.

**6. `VerifySpec` has no successor relation and no demotion.**
`docs/milestones/M5.md:92-94` requires "a test that **enumerates every promotion
transition in the binding** and requires the `clinician-review` successor set to
be empty" — but the only ordering mechanism in the type is the array index
(`docs/design/01-skill-hierarchy.md:204`), so "the last element has an empty
successor set" is trivially true and the claim is vacuous as written. And
`docs/milestones/M6.md:87-89` and `:175-177` both **demote** a Story's rung,
which no field expresses.

**7. `killSwitch?` cannot say "there is no kill switch, deliberately".**
`docs/design/09-security.md:355-362` is the master inventory, and it disagrees
with the binding literals in **four domains of five**: `wealth` declares
`killSwitch: "iai wealth halt --all"`
(`docs/design/07-domain-wealth-know.md:130`) where the inventory says "**Not
applicable — there is no execution path to kill.** The control is capability
absence" (`:360`); `know` omits the field entirely
(`docs/design/07-domain-wealth-know.md:438-450`) where the inventory supplies
one (`:361`). `docs/milestones/M8.md:127-130` then requires a passing test per
row proving "its kill switch **or its capability absence**" — a distinction
`killSwitch?: string` cannot represent.

**8. Nothing forbids `packages/core` from importing a domain pack.**
`docs/milestones/M1.md:237-238` and `CLAIM-9.4` name only the two adapter
packages. `ARCHITECTURE.md:81` and `docs/design/08-dual-target.md:497-499` say
core imports no host and packs never import each other — both silent on
core→pack. `CLAIM-31.6` and `docs/milestones/M4.md:206-208` forbid domain
*literals* in core, which implies the import ban without stating it. The
abstraction's central promise is enforced by nothing.

## Vision

A caller holds a `domain:*` label and a set of bindings supplied by whoever
composed the application. It asks this layer two questions — *is this binding
well-formed* and *which binding does this label name* — and gets back either a
validated binding or a hard failure naming the missing pack. Nothing here reads
a file, imports a pack, or knows that `trade` exists.

The registry is a pure function from a list of bindings to a lookup. Adding a
domain is adding an element to that list, and the list is not in core.

## Constraints

- **Purity, at the standard S1.2, S1.3 and S1.4 hold.** No I/O, no
  `process.cwd()`, no Bun globals, no node builtin. Unlike those three, the
  lint rule and the harness cover this directory **in this Story** (Decision 9).
- **No module-level mutable state.** A `register()` that mutates a module
  singleton is state in a directory the purity harness runs with `process`
  trapped, and it makes resolution order-dependent. The registry is
  constructed, not accumulated (Decision 2).
- **Total functions.** A binding arrives from *another package* — for this
  layer it is untrusted input in the same sense a comment list was for S1.4.
  No hostile value throws.
- **Fail closed.** An unregistered label is a hard-failure `Decision` naming the
  missing pack, never a default binding (`docs/milestones/M1.md:206-208`),
  mirroring `CLAIM-26.3` and `docs/milestones/M3.md:115-117`.
- **Constants are imported, never restated.** `SENTINEL_NAMESPACE_PREFIX` and
  `BUDGET_CHARS` are exported from `packages/core/src/evidence` specifically for
  this Story — Decision 11 of `docs/design/stories/26.md:237`, marked
  `EXPORTED FOR S1.5` at `packages/core/src/evidence/sentinel.ts:48-53` and
  `packages/core/src/evidence/render.ts:35-40`.
- **Core knows no domain.** No import of any `packages/domain-*`, and no domain
  literal outside the declared id union and test fixtures
  (`docs/milestones/M1.md:217-219`).

## Goal

A domain is a value, not a branch. Adding one is writing a binding and putting
it in a list; getting one wrong is a named rejection at registration rather than
a surprise at the gate.

### Decision 1 — the id union is opened, and the deviation is recorded

`CLAIM-31.1` and `CLAIM-31.3` are jointly unsatisfiable while `id` is closed.
The resolution keeps both readable:

```ts
export type KnownDomainId = "dev" | "trade" | "health" | "wealth" | "know";
export type DomainId = KnownDomainId | (string & {});
```

Every literal from `docs/design/01-skill-hierarchy.md:187` survives, in the same
order, in a type that still autocompletes to those five. A sixth domain — and
`nullBinding`, which needs an id no closed union can supply — is assignable
without touching core. `CLAIM-31.6`'s permission for the literals to appear "in
the `id` union type" is satisfied literally: `KnownDomainId` is that union.

**This is a deviation from a claim that says "every field name and type", and it
is recorded rather than hidden.** The alternative readings were tried and
rejected: typing `id: string` discards the five names `CLAIM-31.6` expects to
find; making `nullBinding` masquerade as `dev` makes the conformance suite lie
about what it proves; and widening the union in core for each new domain is the
`if (domain === "trade")` failure in slower motion — `ARCHITECTURE.md:208` names
it as the thing the whole abstraction exists to prevent.

The registry validates `id` as a shape (`^[a-z][a-z0-9-]*$`, non-empty) rather
than as a membership test, because membership is exactly what must stay open.

### Decision 2 — the registry is constructed, and the checklist is corrected

`CONTRIBUTING.md:303` and `docs/milestones/M5.md:82-85` cannot both stand. One
says add a line to `packages/core/src/binding/registry.ts`; the other fails the
build if the story branch touches that directory at all. Four further citations
side with M5 — `docs/milestones/M1.md:209-211`, `:235-236`,
`docs/milestones/M4.md:37-38`, `:230-231`, `docs/milestones/M6.md:39-40` — and
`PLAN.md:211` makes the abstraction leaking the milestone's largest risk. The
checklist is the outlier and it is the document this Story may safely correct.

So:

```ts
export function createRegistry(bindings: readonly unknown[]): RegistryResult;
export function resolveBinding(registry: Registry, label: string): ResolveResult;
```

No `register()`, no module-level `Map`, no side effect. The composition root —
the list — lives with whoever assembles the application, which for this Story is
the conformance suite and for M4 onward is the installer or the adapter.
`docs/design/01-skill-hierarchy.md:419-421`'s "there is no separate registry to
keep in sync" is then true in the sense that matters: **there is no second
source of truth.** The `domain:` label remains the routing key; the registry is
a lookup built from data supplied at the edge.

Two further reasons injection wins. `docs/milestones/M1.md:6-8` requires every
module in this milestone to be "a pure function from input to a `Decision`", and
a mutable module singleton is not. And `docs/milestones/M8.md:85-87` needs Pulse
to render "one surface per domain", which requires the registry to be
**enumerable** — trivial for a constructed value, awkward for an accumulated
one.

`CONTRIBUTING.md`'s checklist item becomes: add the pack to the composition
root's binding list, which is not under `packages/core/src`. That edit is a
Build Target of this Story.

### Decision 4 — a literal type and a runtime check are not redundant

`evidenceRequired: true` makes `false` a compile error, which is the right
protection against the honest mistake. `CLAIM-31.4` still asks for a runtime
rejection, and it is worth keeping for three reachable paths the type system
does not see:

1. A binding authored in JavaScript, or one that crossed a `JSON.parse`.
2. A binding written as markdown. `docs/design/01-skill-hierarchy.md:32-33`,
   `:122`, `:436` and `docs/design/04-domain-dev.md:36` all say the binding is
   `skills/<id>/domain.md`, while `CONTRIBUTING.md:291-293` and
   `ARCHITECTURE.md:154` say it is `packages/domain-<id>/src/binding.ts`. That
   contradiction is unresolved and out of scope here — but if the markdown
   reading ever wins, every field arrives as an unvalidated string and this
   check is the only thing standing.
3. An `as any` cast, which is how the test fixture must construct the invalid
   value.

The tests therefore construct the negative fixtures **through an unsound cast**,
and the Design says so, because a fixture that cannot be built is a case that
silently passes. The same reasoning covers `Rung.verifier`, `EvidenceSpec.pinned`
and every other literal-typed field.

### Decision 5 — the sentinel must be one of the nine

`packages/core/src/evidence/sentinel.ts:88-98` ships `isSentinelNamespace` as a
**prefix** test and states plainly why the choice was left open:

> the claim's words are "falls outside the `## iai-` namespace", which is a
> weaker condition than "is one of the nine". A binding naming
> `## iai-something-new` is inside the namespace and outside the set, and **only
> S1.5 can decide whether that is an error**.

It is an error. The nine names are a closed set
(`docs/design/03-workflow.md:372-382`), S1.4's matcher and linter recognise
exactly those nine, and a pack that invents `## iai-audit` produces a comment
that the producer will write and the consumer can never find. Accepting it would
ship a sentinel with no reader.

So `CLAIM-31.5` is implemented as four rules, two of them stronger than its
words, and both strengthenings are recorded here:

| Rule | Source |
|---|---|
| outside `## iai-` → reject | `CLAIM-31.5`, literal |
| inside the prefix, outside the nine → reject | this Decision, strengthening |
| `budgetChars > BUDGET_CHARS` → reject | `CLAIM-31.5`, literal, using the imported constant |
| `pathTemplate` present for a non-artifact-bearing sentinel → reject | Decision 10 of `docs/design/stories/26.md:388-396`, inherited |

A binding may declare a `budgetChars` **below** 60,000. Reserving less than the
budget is safe; the rejection rule is one-sided by construction.

### Decision 6 — the interface ships as declared, and what that costs is named

Problems 5 and 6 describe four fields whose declared type cannot support what a
later milestone asks of it. The temptation is to fix them here. That is refused,
for the reason `CLAIM-31.1` exists: the interface is transcribed into
`references/domain-binding.md` in M2 and instantiated five times in M4 through
M7, and inventing structure now — a predicate DSL for `entryCriteria`, a numeric
threshold pair for sizing, a tagged union for `autoDeny` — would be authoring a
language against zero real callers. S1.4's Decision 6 authored a summary
envelope from one example and was right to flag it; this is four times the
surface with none.

What this Story does instead is name the debt precisely, so each milestone
inherits a decision rather than discovering a gap:

| Field | Declared | Claim that needs more | Owner |
|---|---|---|---|
| `unitOfWork.minSize` / `maxSize` | `string` prose | `CLAIM-56.4` (`M2.md:206-207`), `CLAIM-111.5` (`M5.md:95-97`) — reject below/above with the reason stated | M2's `size` |
| `Rung.entryCriteria` | `string[]` prose | `CLAIM-111.3` (`M5.md:89-91`) — evaluated as a predicate over disk state | M5 |
| `GateSpec.autoDeny` | `string[]` prose | `CLAIM-157.4` (`M6.md:253-256`), `CLAIM-83.6` (`M4.md:50-51`) — each condition independently refuses | M6 |
| promotion transitions | array order only | `CLAIM-111.4` (`M5.md:92-94`) — enumerate transitions, empty successor set. **Vacuous against an array** | M5 |
| demotion | absent | `CLAIM-137.3` (`M6.md:87-89`), `CLAIM-147.5` (`M6.md:175-177`) — demote a Story's rung | M6 |

Two consequences follow and are stated so nobody has to rediscover them.
`docs/milestones/M2.md:220`'s "binding supplies thresholds" is true only in the
sense that the binding supplies *prose thresholds*, so `size` is **model-judged
against a written bound, not tool-checked against a number** — and any test plan
that anchors `CLAIM-56.4` to a `tool-checked` verifier is anchoring to a
capability the interface does not have. And `CLAIM-111.4` as written is
satisfied trivially by any array; M5 must either add a `promotesTo` field or
rewrite the claim against the ordering.

Each is a widening when it lands. Adding an optional structured field beside a
prose one keeps every existing binding compiling, which is why deferring costs
little and guessing costs a rename in seven places.

### Not resolved here, and deliberately

- **Where the binding physically lives.** Nine citations say
  `skills/<id>/domain.md`; four say `packages/domain-<id>/src/binding.ts`;
  `docs/milestones/M4.md:56` says both in one table row.
  `docs/design/verification-pass.md:253` already logs it `corrected` without
  deciding. This Story declares a TypeScript interface, which is what
  `CLAIM-31.1` and `CONTRIBUTING.md:291-293` require and what M4 will
  instantiate; if the markdown reading later wins, the interface is unchanged
  and a parser is added in front of it. Decision 4's runtime checks are what
  make that survivable.
- **The `repo` field.** `docs/design/09-security.md:323-327` requires the
  binding to carry `owner/repo` so private-domain issues route to the private
  repository. There is no field and no claim. Adding one is a widening, needed
  first by M5.
- **`vetoAgent`'s meaning.** `docs/design/01-skill-hierarchy.md:222` says
  "absolute, non-overridable veto"; `docs/design/02-roles.md:374` grants that to
  `risk-officer` alone, yet `health`, `wealth` and `know` each name an agent
  that `02-roles.md` gives no veto — and `know` names `iai-librarian`, a Ring 1
  advisor that "cannot be assigned work" (`docs/design/02-roles.md:9-10`).
  Three of five instances are unimplementable under the current roster. The
  field is declared as specified; the roster conflict belongs to M3 and to each
  pack's Story.
- **The rung colour ramp.** `docs/design/03-workflow.md:130-131` mandates one
  ramp; all five bindings deviate; `scripts/bootstrap-github.sh:93-135`
  implements the mandated ramp for all twenty labels. `CLAIM-111.6` will make
  `/iai:init` reconcile a drifted colour, at which point the script and the
  bindings fight. Recorded; not this Story's to settle.
- **Two `domain:*` labels on one issue.** `docs/design/03-workflow.md:151`
  states the invariant and names no enforcement point, unlike `status:*` at
  `:165-166`. `CLAIM-31.2` covers absence and non-membership; multiplicity is a
  label-hygiene rule that belongs with the workflow guard.
- **`DomainId` name collision.** All five `packages/domain-*/src/index.ts`
  already export an interface named `DomainId` meaning an object with one
  field. Core will export a type of that name meaning a string. The stubs are
  replaced wholesale in M4 through M7, so the collision is transient — but a
  pack importing both before then will need an alias.
