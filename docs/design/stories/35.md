# S2.1 — Kernel reference documents

**Story:** #35 · **Milestone:** M2 — Universal lifecycle
**Unit of work:** one reference document
**Creates:** `references/` — the twelve contract documents
**Widens:** `scripts/skill-lint.ts` (body rules), `packages/core/src/guards/path-allowlist.ts` (twelve retirements)
**Corrects:** `docs/milestones/M2.md` (three claims restated), `docs/design/01-skill-hierarchy.md` (two ownership collisions)

S1.5's difficulty was two of its six claims being jointly unsatisfiable. S2.1's
is worse in kind and worse in degree: **four of its six claims cannot be
verified by this Story at all**, because three of them govern a population —
skills — that this Story does not create, and the fourth names an exemption
directory that a later milestone builds. The reference layer itself is
straightforward. Everything the milestone asks us to *prove* about it is not.

some time.** `docs/design/verification-pass.md:192` verdicts the identical

## Vision

Twelve contract documents exist under `references/`. Each states one contract
once. A skill that needs the label state machine reads
`references/workflow-states.md` by explicit path at the moment it needs it; the
host never enumerates the file, so it costs nothing until it is read. When the
commit-prefix regex changes, exactly one document changes with the code.

The layer is boring on purpose. What this Story actually delivers is the
*reconciliation* — the table proving each normative statement in each reference
matches the design documents and the M1 implementation, with every disagreement
either fixed or recorded with an owner. The documents are the easy half.

## Constraints

- **A reference states a contract once and cites nothing back into itself.** The
  whole point (`docs/design/01-skill-hierarchy.md:41-49`).
- **References are never registered as skills.** No frontmatter that a host
  roster would read, no `SKILL.md` naming.
- **Where a contract already exists in code, the reference describes it and
  names the owning module.** It must not become a second normative source —
  which is what "mirrors the M1 interface" (`docs/milestones/M2.md:61`) invites.
- **Provenance markers survive transcription.** `docs/design/stories/21.md:280-282`
  requires the exit-code taxonomy's `assumed` markers to reach
  `references/gh-error-handling.md` intact rather than being "laundered into
  fact by being copied".
- **Every file created retires its allow-list entry in the same commit.**

### Decision 1 — the model-ID ban is scoped to what we author

`CLAIM-35.3`'s intent is legible at `docs/design/01-skill-hierarchy.md:398-400`:
*"a model change is a routing-table edit, never sixty frontmatter edits"*. The
target is **authored artefacts that carry a model ID as configuration** — skill
and agent frontmatter — not prose that discusses model routing.

Read literally, the claim fails on `docs/design/02-roles.md:547-553`, which *is*
the routing table the reference must transcribe; on `ARCHITECTURE.md:149`; and
on two guard files where a model ID is the canonical false-positive fixture for
`path-refs`. Deleting a NEVER-class guard's test fixture to satisfy a
documentation claim is a bad trade.

So the rule scans `skills/`, `agents/` and `references/`, permitting exactly
`references/model-routing.md`. This is the same posture as Decision 3 of
`docs/design/stories/26.md` and Decision 1 of `docs/design/stories/31.md`:
restate the claim to what is true and enforceable, and record the deviation,
rather than ship a rule that fails the repository's own documents.

The prose sites are not left unrecorded — they are the reconciliation table's
first rows, and `docs/design/verification-pass.md:192` already carries the
verdict.

### Decision 2 — the duplicate-contract rule polices three literals, not similarity

"Restates the contract" is undecidable in general. The claim names three
contracts, and all three have a **mechanically detectable canonical form**:

- the sentinel namespace prefix `## iai-`, exported as
  `SENTINEL_NAMESPACE_PREFIX`;
- the at-most-one-`status:` invariant, whose enforcement is
  `EXCLUSIVE_LABEL_PREFIXES` in `packages/core/src/gh/labels.ts:54`;
- the commit-prefix regex, exported as `COMMIT_PREFIX_RE` at
  `packages/core/src/guards/commit-prefix.ts:12`.

The rule fails a skill body containing the regex literal, or the label
invariant stated as a rule rather than as a citation, unless the body also cites
the owning reference by path. No tokenizer, no fingerprinting, no similarity
threshold — a rule nobody can predict is a rule nobody will trust.

**It ships with fixtures, because `skills/` is empty.** A body rule merged
against an empty corpus is the `skill-lint` failure exactly: required in CI,
green on every run, checking nothing. Three negative fixtures and one positive,
plus a mutation proving each fires, following #253, #261 and #272.

**It does not police `references/` for these three.** A reference is the place
the contract is stated; that is `NEVER-35.7`'s separate and narrower job, which
bans restating a *code-exported constant* rather than the prose contract.

### Decision 3 — prove the predicate, not the population

`CLAIM-35.4` and `CLAIM-35.5` are about skills, and this Story writes none. Two
honest options existed: defer both to S2.2, or prove here what can be proved and
name the rest.

Deferring loses the mechanism. So each is split: **the predicate is built and
tested here**, against fixtures, with a denominator asserted; **the live count
over real skills belongs to S2.2**, where a real skill exists to count.

For `CLAIM-35.4` this also removes a dependency on M8. "The installed skill
roster contains zero `references/` entries" cannot be checked before an
installer exists. What *can* be checked, and is the property that matters, is
that the roster-discovery predicate — the same `SKILL.md` basename match
`scripts/skill-lint.ts` already implements — returns nothing for `references/`,
over a denominator of twelve real files. If a reference ever grew skill
frontmatter, that is what would catch it.

### Decision 5 — `isa-format` is renamed to `design-format`

> **AMENDED AT THE GATE, 2026-09-05.** The human decider ruled that the file is
> renamed to `design-format`, taking the recommendation this Decision put to the
> gate. **iAI did not originate the decision.** The reasoning below is preserved
> as the record of what was put and why; the ruling that follows it supersedes
> its conclusion, not its analysis.
>
> [†] **One mechanical edit was necessary, and it is marked.** The paragraph
> below originally wrote the name as the repo-relative path
> `references/` + `isa-format.md`. Once the allow-list entry was renamed, that
> spelling became a genuine dangling-path citation and `claim-lint`'s
> `path-dangling` rule failed the build on it — correctly. It is now written as a

> there permanently, exempting the path forever. No other word is changed.

As written before the gate, Problem 11 was recorded and not resolved. Three
reasons, in order of weight:

1. **An agent may never author a decision** (`docs/design/03-workflow.md:271`).
   Renaming a file the milestone names explicitly, that
   `docs/design/01-skill-hierarchy.md:63` and `:94` both cite, and
   `packages/core/src/guards/path-allowlist.ts` pins, is a vocabulary decision
   belonging to whoever owns S1.6's retirement.

### Decision 11 — `skill-lint` gets two populations, not one scope

> **ADDED AFTER THE GATE, 2026-09-05, on a human decision.** Decided by
> @dev-pmallapp; recorded by iAI with attribution. **iAI did not originate it.**
> The instruction was to widen the scope, *carefully*. This Decision is what
> "carefully" resolves to, and it is a Build Target change.

`docs/test-plans/35-plan.md` case 21 raised the gap: **the tool named in the Test
Strategy cannot see the files it is asked to scan.** `scripts/skill-lint.ts:386-397`'s
`discoverSkillFiles` matches `SKILL.md` by exact basename, `main()` defaults its
target to `skills/`, `.github/workflows/ci.yml:107` pins `bun run skill-lint
skills/`, and `CONTRIBUTING.md:113` states the same. `CLAIM-35.3` and
`NEVER-35.7` both name `bun run skill-lint` and both require scanning
`references/`.

**The naive widening is wrong, and measurably so.** Pointing the existing
discovery at `references/` and letting `lintSkillSource` run produces
`frontmatter-missing` for **every one of the twelve** — verified against the real
function, not reasoned about. That is precisely what
`docs/design/verification-pass.md:142` (conflict row 19) meant by *"one schema
cannot span all three"*, and why `docs/milestones/M1.md:62` says the linter
*"does not sweep the docs targets"*.

**Row 19 is not reversed. It is scoped.** The adjudication it records is about
the **frontmatter schema**, and that ruling stands unchanged: a reference
document has no frontmatter and must never be asked for one; an agent file must
omit `name` on opencode. What row 19 never considered is a **body** rule, because
none existed when it was written — all eleven rules in `RULE_IDS` at
`scripts/skill-lint.ts:409-421` are frontmatter rules. This Story adds the first
three body rules in the repository.

So the linter grows **two populations with two rule sets**:

| Population | Discovery | Rules applied |
|---|---|---|
| `skills/**/SKILL.md` | exact basename `SKILL.md`, unchanged | all frontmatter rules **plus** the three new body rules |
| `references/*.md`, `agents/*.md` | any `.md` | **body rules only** — no frontmatter rule may fire |

Four consequences, each a task deliverable:

1. `discoverSkillFiles` keeps its exact-basename contract and is **not**
   loosened. A second discovery function is added beside it. Widening the
   existing one is the single most likely way to reintroduce the twelve
   `frontmatter-missing` errors.
2. The CI invocation at `ci.yml:107` and the command in `CONTRIBUTING.md:113`
   both change, and `docs/milestones/M1.md:62`'s "does not sweep the docs
   targets" is annotated — **not silently falsified**. M1 shipped exactly what it
   said; this Story extends it.
3. **A body rule must never fire on a frontmatter defect, and a frontmatter rule
   must never fire outside `skills/`.** Both directions are asserted, because a
   one-directional check would pass while the other leaks.
4. The report line must distinguish the two counts. `skill-lint: 0 SKILL.md files
   scanned` is the repository's standing example of a vacuous pass; a widened
   linter that prints one conflated number would hide a zero in either
   population.

**Row 19 is annotated, not edited.** `docs/design/verification-pass.md`'s verdict
rows are immutable by Decision 9, and this Story does not get to rewrite one. The
reconciliation is recorded here and cited from the task.
